Сортировки: merge, quick и почему O(n log n)

Вопрос #5 входного теста — у какой сортировки O(n log n) даже в худшем случае — был провален. Урок по O-нотации разбирал, как считать сложность, но не сами алгоритмы. Здесь разберём три из них и главное: откуда вообще берётся log n и почему быстрее уже нельзя.

Откуда берётся n log n

Сортировка сравнением — это последовательность вопросов «a больше b?». Каждый ответ даёт один бит информации и делит множество возможных порядков надвое.

Порядков у n элементов ровно n!. Чтобы выделить один из них, нужно как минимум log₂(n!) сравнений, а это по формуле Стирлинга примерно n log n.

Отсюда важное следствие. O(n log n) — не «пока не придумали лучше», а доказанная нижняя граница для любой сортировки, основанной на сравнениях. Быстрее можно только отказавшись от сравнений вовсе.

Сортировка слиянием (merge sort)

Схема «разделяй и властвуй»: массив делится пополам, каждая половина сортируется рекурсивно, отсортированные половины сливаются.

function mergeSort(a) {
  if (a.length <= 1) return a;
  const mid = a.length >> 1;
  return merge(mergeSort(a.slice(0, mid)), mergeSort(a.slice(mid)));
}

function merge(l, r) {
  const out = [];
  let i = 0, j = 0;
  while (i < l.length && j < r.length) {
    out.push(l[i] <= r[j] ? l[i++] : r[j++]);   // <= сохраняет стабильность
  }
  return out.concat(l.slice(i), r.slice(j));
}

Слияние двух отсортированных массивов линейно: каждый элемент берётся ровно один раз, потому что сравнивать нужно только головы. Уровней деления log n, на каждом уровне суммарно n работы — отсюда n log n.

СвойствоЗначение
Худший случайO(n log n) — всегда, вход ни на что не влияет
ПамятьO(n): нужен дополнительный массив
Стабильностьда

Это и есть ответ на вопрос теста: merge sort даёт O(n log n) даже в худшем случае, потому что деление пополам не зависит от данных.

Быстрая сортировка (quicksort)

Тоже «разделяй и властвуй», но делит не по позиции, а по значению: выбирается опорный элемент, массив разбивается на «меньше опорного» и «больше», каждая часть сортируется рекурсивно.

выбрали опорный 5
[3 7 1 9 5 2 8]  →  [3 1 2] 5 [7 9 8]
                     сортируем обе части тем же способом

В среднем опорный делит массив примерно пополам, уровней снова log n, итого O(n log n). Но если опорный каждый раз оказывается минимумом или максимумом, одна часть пуста, а вторая короче лишь на элемент — уровней становится n, и сложность вырождается в O(n²).

Классическая ловушка. Если опорным всегда брать первый элемент, худший случай — уже отсортированный массив. Практически это встречается постоянно: данные часто приходят упорядоченными. Лечится случайным выбором опорного или медианой из трёх.

При этом на практике quicksort обычно быстрее merge sort с той же асимптотикой: он работает на месте, не выделяет память и хорошо ложится на кеш процессора — константа под O меньше.

Сортировка вставками при квадратичной сложности не бесполезна: на почти отсортированных данных она близка к линейной и на коротких массивах обгоняет всех за счёт крошечной константы. Поэтому реальные реализации переключаются на неё для кусков в десяток элементов.

Стабильность

Стабильная сортировка сохраняет исходный порядок элементов с равными ключами. Это не мелочь: на стабильности держится сортировка по нескольким полям.

Отсортировать по отделу, внутри отдела — по имени:

  1) сортируем по имени
  2) сортируем по отделу стабильной сортировкой
  → внутри отдела имена остались упорядоченными

С нестабильной сортировкой второй проход разрушит результат первого.

Что происходит на самом деле

Реальные реализации — гибриды. Timsort (Python, Java для объектов) ищет во входе уже упорядоченные куски и сливает их; на почти отсортированных данных выходит на O(n). Introsort (C++) начинает как quicksort и переключается на пирамидальную, если глубина рекурсии стала подозрительной, — так гарантируется O(n log n) в худшем случае.

В JavaScript Array.prototype.sort с 2019 года обязан быть стабильным по спецификации; V8 использует Timsort. Две вещи о нём стоит помнить всегда:

[10, 9, 1].sort()              // [1, 10, 9] — сравнение как строк!
[10, 9, 1].sort((a, b) => a - b)  // [1, 9, 10]

const sorted = arr.sort()      // sort мутирует arr и возвращает его же
const copy = [...arr].sort()   // или arr.toSorted() в новых средах

Когда сортировка не нужна

  • Нужен минимум или максимум — это один проход за O(n), сортировать незачем.
  • Нужны k наибольших — куча даёт O(n log k) вместо O(n log n).
  • Нужна медиана — алгоритм быстрого выбора даёт O(n) в среднем.
  • Нужен только поиск — хеш-таблица даёт O(1) без всякого порядка.

И отдельный случай: если ключи — небольшие целые числа, сравнения можно не делать вовсе. Сортировка подсчётом работает за O(n + k), где k — диапазон значений, обходя доказанную границу именно потому, что не сравнивает элементы между собой.

Что уносим с собой. O(n log n) — доказанная нижняя граница для сортировок сравнением. Merge sort даёт её всегда, ценой O(n) памяти. Quicksort в среднем быстрее, но вырождается в O(n²) при неудачном опорном — классически на отсортированном входе. Стабильность нужна для сортировки по нескольким полям. sort() в JS мутирует массив и без компаратора сравнивает строки.
