Сложность алгоритмов: O-нотация

Во входном тесте ты угадывал почти все вопросы этого блока: 9 из 12. Это не пробел в знаниях — это пробел в языке, на котором про производительность вообще говорят. Разберёмся один раз.

Зачем это нужно на практике

Ты пишешь функцию, она работает на 10 записях. В продакшене их 50 000, и страница виснет на 8 секунд. Вопрос «а выдержит ли этот код рост данных?» решается не замером, а прикидкой в уме. O-нотация — как раз инструмент такой прикидки.

Она отвечает на один вопрос: как растёт время работы, когда растёт объём входных данных. Не «сколько миллисекунд», а «во сколько раз хуже станет, если данных станет вдвое больше».

Главное правило: константы не важны

Запись O(n) читается «порядка n». Внутри отбрасывают всё, кроме самого быстрорастущего слагаемого, и все множители:

  • 3n + 100 → O(n)
  • n² + 1000n → O(n²), потому что при большом n именно n² определяет всё
  • 5 → O(1)

Кажется грубым, но в этом и смысл: алгоритм O(n²) при росте данных проиграет алгоритму O(n) при любых константах — надо лишь дождаться достаточно большого n.

Правый столбец — вся суть. Разница между O(n) и O(n²) на миллионе элементов это разница между «мгновенно» и «неделя».

Почему доступ по индексу — это O(1)

В тесте ты ответил O(log n). Логарифм появляется там, где что-то делится пополам. Здесь ничего делить не нужно.

Массив в памяти — это непрерывный кусок ячеек одинакового размера. Чтобы найти arr[734], процессор не идёт по элементам, а считает адрес одной формулой:

адрес = адрес_начала + 734 × размер_элемента

Одно умножение и одно сложение — независимо от того, 10 элементов в массиве или 10 миллионов. Поэтому O(1).

Для сравнения: в связанном списке (linked list) элементы разбросаны по памяти и каждый хранит ссылку на следующий. Чтобы добраться до 734-го, нужно пройти 734 ссылки — это уже O(n).

Почему бинарный поиск — это O(log n)

В тесте ты ответил O(n). O(n) — это обычный перебор. Бинарный поиск заметно умнее, но требует, чтобы массив был уже отсортирован.

Алгоритм: смотрим на элемент в середине. Если искомое меньше — выбрасываем всю правую половину, если больше — левую. Повторяем.

Ищем 73 среди 1..100
шаг 1: середина 50 → 73 больше → остаётся 51..100
шаг 2: середина 75 → 73 меньше → остаётся 51..74
шаг 3: середина 62 → 73 больше → остаётся 63..74
шаг 4: середина 68 → ...  осталось 6 вариантов
шаг 5: ... 3
шаг 6: ... 1  — нашли

Каждый шаг уменьшает область поиска вдвое. Вопрос «сколько раз можно поделить n пополам, пока не останется один элемент?» — это и есть определение логарифма по основанию 2.

  • 1 000 элементов → 10 шагов
  • 1 000 000 элементов → 20 шагов
  • 1 000 000 000 элементов → 30 шагов

Данных стало в тысячу раз больше — работы прибавилось на 10 шагов. Вот почему логарифм считается почти таким же хорошим, как константа.

Сортировки: средний случай против худшего

В тесте ты ответил «пузырьком». Пузырьковая сортировка — наоборот, эталон медленного: два вложенных прохода, O(n²) всегда.

Важная тонкость: у алгоритма может отличаться поведение на «удачных» и «неудачных» данных.

АлгоритмСредний случайХудший случай
ПузырькомO(n²)O(n²)
Быстрая (quicksort)O(n log n)O(n²)
Слиянием (merge sort)O(n log n)O(n log n)

Quicksort выбирает опорный элемент и делит массив относительно него. Если опорный каждый раз оказывается самым маленьким (например, массив уже отсортирован, а берём первый элемент), деления пополам не происходит — получаем O(n²).

Merge sort всегда делит массив ровно пополам, независимо от данных — потому гарантия O(n log n) и держится. Плата за гарантию: ему нужна дополнительная память под слияние.

Кстати, Array.prototype.sort() в V8 — это Timsort, гибрид сортировки слиянием и вставками, тоже O(n log n) в худшем случае.

Как оценить свой код за 5 секунд

Считай вложенность циклов по данным:

// O(n) — один проход
items.forEach(item => console.log(item));

// O(n²) — цикл в цикле
for (const a of items) {
  for (const b of items) { compare(a, b); }
}

// O(n²), хотя вложенности не видно!
// includes сам по себе O(n), и он внутри цикла по n
const dupes = items.filter(item => other.includes(item));

Последний пример — самая частая скрытая проблема во фронтенде. Лечится структурой данных с быстрым поиском:

// O(n): построение Set — O(n), каждая проверка has — O(1)
const otherSet = new Set(other);
const dupes = items.filter(item => otherSet.has(item));

На массивах по 10 000 элементов это разница примерно в тысячу раз. Тот же приём — с Map вместо array.find() внутри цикла.

Что уносим с собой. O(1) — прямой адрес. O(log n) — что-то делится пополам. O(n) — один проход. O(n log n) — хорошая сортировка. O(n²) — цикл в цикле, в том числе спрятанный внутри includes, find или indexOf.
