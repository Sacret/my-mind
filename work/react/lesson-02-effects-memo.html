Эффекты, зависимости и мемоизация

Продолжение первого урока. Там состояние появлялось и доставлялось вниз; здесь — что происходит после его изменения, как связать компонент с внешним миром, не поймав гонку и устаревшее замыкание, и почему useMemo в половине случаев не помогает.

Что на самом деле стоит ререндер

Слово «перерисовка» сбивает: кажется, что React каждый раз трогает DOM. На деле обновление идёт в три шага.

  1. Рендер — React вызывает функцию компонента и получает описание разметки: обычные объекты, а не элементы DOM.
  2. Сверка — новое описание сравнивается с предыдущим и получается список отличий.
  3. Коммит — только отличия применяются к настоящему DOM, после чего браузер рисует кадр.

Дорогой шаг почти всегда третий, а лишние рендеры сами по себе дёшевы: вызвать функцию и сравнить два объекта — быстро. Отсюда практический вывод, который экономит много времени: гоняться за «лишними рендерами» до того, как замечено торможение, бессмысленно. Проблемой они становятся, когда на каждый рендер приходится тяжёлая работа — сортировка десяти тысяч строк, разбор большого текста, — или когда рендерится сразу огромное поддерево.

Из первого урока. Изменилось состояние — рендерится компонент и всё его поддерево, потому что props React автоматически не сравнивает. Это ровно та причина, по которой ниже понадобится React.memo.

Обновления состояния батчатся

Несколько setState внутри одного обработчика дают один рендер, а не по одному на вызов — React собирает их в пачку и применяет разом:

function onClick() {
  setName("Аня");
  setAge(30);
  setCity("Тбилиси");   // рендер будет один, после выхода из обработчика
}

Поэтому «объединю три состояния в один объект, чтобы рендер был один» — не аргумент: он и так один. Объединять стоит только то, что действительно меняется вместе и по смыслу является одной величиной.

Правила хуков и почему они такие

Хуки нельзя вызывать в условии, цикле или после раннего return. Причина не в стилистике: React не знает имён твоих переменных и сопоставляет вызовы с сохранёнными значениями по порядку. Первый useState в компоненте — первая ячейка, второй — вторая.

function Profile({ user }) {
  if (!user) return null;          // ← ранний выход
  const [tab, setTab] = useState("info");   // на разных рендерах это то первая ячейка, то её нет
  …
}

Как только количество вызовов между рендерами меняется, нумерация съезжает и состояние достаётся не тому хуку. Отсюда правило: все хуки — на верхнем уровне компонента, до любых ветвлений; условие переносится внутрь хука, а не оборачивает его.

useEffect: не «сделать что-то после рендера», а синхронизация

Самая частая ошибка — считать useEffect местом, куда складывают код, который должен «просто выполниться». Правильная формулировка: эффект синхронизирует компонент с чем-то за пределами React — подпиской, таймером, сетевым запросом, заголовком вкладки, сторонней библиотекой.

Из этого следуют два случая, когда эффект не нужен.

Не нужен для производных данных. Классика, которая даёт лишний рендер и рассинхрон:

// плохо: сначала рендер со старым filtered, потом эффект, потом второй рендер
const [filtered, setFiltered] = useState([]);
useEffect(() => { setFiltered(items.filter(i => i.active)); }, [items]);

// хорошо: значение вычисляется прямо при рендере
const filtered = items.filter(i => i.active);

Не нужен для реакции на действие пользователя. Если что-то должно произойти именно по клику, код принадлежит обработчику клика. Заводить состояние submitted и следить за ним эффектом — окольный путь: причина события теряется, и потом невозможно понять, отчего эффект сработал.

Массив зависимостей

Второй аргумент — список значений, которые эффект читает снаружи. Перед каждым рендером React сравнивает их с предыдущими через Object.is, то есть по ссылке, и запускает эффект заново, только если что-то изменилось.

ЗаписьКогда выполняется
без второго аргументапосле каждого рендера
[]один раз при монтировании
[a, b]при монтировании и при каждом изменении a или b

Соблазн выкинуть из списка мешающую зависимость приводит к устаревшему замыканию: эффект помнит те значения, что были в момент его создания.

useEffect(() => {
  const id = setInterval(() => setCount(count + 1), 1000);
  return () => clearInterval(id);
}, []);            // count здесь навсегда 0 → счётчик застревает на единице

Лечится не добавлением count в зависимости (тогда интервал будет пересоздаваться каждую секунду), а функциональной формой — той же, что в первом уроке:

setCount(c => c + 1);   // старое значение приходит аргументом, зависимость не нужна
Правило. Зависимости не выбираются — они вычитываются из тела эффекта: всё, что эффект читает из пропсов, состояния и переменных компонента, обязано быть в списке. Если список получается неудобным, менять надо сам эффект, а не список.

Функция очистки

Всё, что эффект «включил», он обязан уметь выключить: подписку — отписать, таймер — снять, запрос — пометить неактуальным. Возвращённая из эффекта функция вызывается перед следующим запуском и при размонтировании.

Без очистки получается гонка, которую тяжело поймать: пользователь быстро переключает пользователя с 1 на 2, ответ по первому приходит вторым, и в состоянии оказываются чужие данные.

useEffect(() => {
  let ignore = false;
  fetch("/api/user/" + id)
    .then(r => r.json())
    .then(data => { if (!ignore) setUser(data); });
  return () => { ignore = true; };   // ответ по старому id больше никого не интересует
}, [id]);

Заметь: отменяется не запрос, а применение его результата, — и этого достаточно, чтобы в состоянии всегда лежал ответ на последний заданный вопрос.

Почему эффект срабатывает дважды

В режиме разработки под <StrictMode> React намеренно монтирует компонент, размонтирует и монтирует снова. Это не баг и не то, что нужно «чинить» флажком didInit: так вылезают именно те эффекты, у которых нет корректной очистки. В сборке для продакшена двойного вызова нет. Эффект, который переживает повторный запуск без последствий, переживёт и всё остальное.

Мемоизация: три разных инструмента

Их постоянно путают, хотя задачи у них разные.

ИнструментЧто кэшируетЗачем
useMemoрезультат вычисленияне считать тяжёлое заново; сохранить ссылку на объект или массив
useCallbackсаму функциюсохранить ссылку на колбэк между рендерами
React.memoрезультат рендера компонентапропустить рендер, если props не изменились

Ключевая связка: React.memo сравнивает props поверхностно, по ссылке. Поэтому обёртка сама по себе часто не работает:

const Row = React.memo(function Row({ onSelect }) { … });

function List() {
  return <Row onSelect={() => …} />;   // новая функция на каждом рендере → memo бесполезен
}

Стрелка создаётся заново при каждом рендере родителя, props «меняются», и memo честно перерисовывает. Чтобы обёртка заработала, колбэк нужно стабилизировать — useCallback, — и то же самое касается любых объектов и массивов в props. То есть useCallback имеет смысл ровно тогда, когда на другом конце кто-то сравнивает ссылки: React.memo или список зависимостей другого хука.

Цена и когда не надо

Мемоизация не бесплатна: значения занимают память, зависимости сравниваются на каждом рендере, а код становится заметно шумнее. Оборачивать useMemo сложение двух чисел — чистый минус.

Признаки, что мемоизация уместна:

  • вычисление действительно тяжёлое и попадает в кадр — сортировка, фильтрация большого списка, разбор текста;
  • значение уходит в зависимости хука или в memo-компонент, и важна стабильная ссылка;
  • значение кладут в value контекста — тот самый случай из первого урока.

И приём, который почти всегда лучше мемоизации: переставить компоненты. Если тяжёлое поддерево не зависит от часто меняющегося состояния, его можно передать через children — тогда оно не будет рендериться вместе с родителем вообще, без всяких обёрток.

Что уносим с собой. Рендер — это вызов функции и сравнение описаний; дорог только коммит в DOM. Хуки вызываются по порядку, поэтому всегда на верхнем уровне. useEffect нужен для синхронизации с внешним миром, а не для производных данных и не вместо обработчика; зависимости вычитываются из тела эффекта, а очистка обязательна — она же лечит гонку ответов. Двойной вызов под StrictMode — проверка очистки, а не баг. React.memo сравнивает props по ссылке, поэтому работает только вместе со стабильными колбэками и объектами; до жалоб на скорость мемоизация чаще вредит, чем помогает.
