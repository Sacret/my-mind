Состояние, поднятие и Context

В тесте «поднятие состояния» ты определила как использование Context. Это близкие темы, и путают их постоянно — но решают они разные задачи, и выбор не того инструмента даёт приложение, где половина компонентов перерисовывается на каждый чих.

Что такое состояние и почему компонент перерисовывается

Компонент — функция, которая по входным данным возвращает разметку. Входных данных два вида: props приходят сверху и принадлежат родителю, state принадлежит самому компоненту и переживает перерисовки.

Обычная переменная внутри функции не годится: при каждом вызове она создаётся заново, и изменение её не заставит React ничего перерисовать. useState решает обе задачи — хранит значение между вызовами и сообщает React, что пора обновиться.

const [count, setCount] = useState(0);

Компонент перерисовывается ровно по трём причинам:

  1. изменилось его собственное состояние;
  2. перерисовался родитель (по умолчанию — независимо от того, изменились ли props);
  3. изменилось значение контекста, который он читает.

Второй пункт удивляет, но он важен: React не сравнивает props автоматически. Перерисовался родитель — перерисуется всё поддерево. Обычно это дёшево, потому что React сравнивает результат с предыдущим и трогает DOM только там, где есть разница.

Сравнение по ссылке. Решение «изменилось ли состояние» React принимает через Object.is, то есть сравнивает ссылки. Поэтому items.push(x) с последующим setItems(items) не вызывает рендера: содержимое другое, адрес прежний. Это ровно та тема, что была в уроке про мутации.

Два правила про useState, которые экономят часы

Обновления асинхронны в пределах обработчика. Значение count внутри текущего вызова не изменится после setCount — оно захвачено замыканием. Если новое состояние зависит от старого, передавай функцию:

setCount(count + 1);
setCount(count + 1);      // прибавится единица: оба раза count — старое значение

setCount(c => c + 1);
setCount(c => c + 1);     // прибавится двойка

Производное не хранят в состоянии. Если значение вычисляется из другого состояния или props — вычисляй его при рендере, а не заводи ещё один useState с синхронизацией через эффект. Два источника правды рано или поздно разъедутся.

// плохо: fullName придётся руками поддерживать при каждом изменении
const [fullName, setFullName] = useState("");

// хорошо
const fullName = firstName + " " + lastName;

Поднятие состояния

Вот определение, ради которого урок и написан: поднятие состояния — это перенос состояния в ближайшего общего родителя двух компонентов, которым нужно одно и то же значение.

Задача выглядит так. Есть список фильтров и есть таблица. Оба должны знать текущий фильтр: один его меняет, другая по нему отображает данные. Состояние внутри Filters для Table недоступно — компоненты видят только своих детей.

function Page() {
  const [filter, setFilter] = useState("all");   // ← общий родитель

  return (
    <>
      <Filters value={filter} onChange={setFilter} />
      <Table filter={filter} />
    </>
  );
}

Схема получается односторонней: данные вниз через props, события вверх через колбэки. Компонент, у которого значение приходит извне, а изменение уходит наружу, называют управляемым — в нём нет своего состояния, и он всегда согласован с родителем.

Обратная процедура тоже полезна: если состояние живёт наверху, но нужно ровно одному потомку, его опускают вниз. Тогда его изменение перестаёт перерисовывать всё дерево.

Когда props перестают справляться

Если общий родитель — прямой сосед, поднятие идеально. Проблема появляется, когда значение нужно на десять уровней ниже, и все промежуточные компоненты вынуждены принимать пропс, который им самим не нужен, только чтобы передать дальше. Это называют прокидыванием пропсов (prop drilling).

<App theme> → <Layout theme> → <Sidebar theme> → <Menu theme> → <Item theme>

Плохо тут не количество строк, а связанность: Layout и Sidebar теперь знают про тему, хотя ничего с ней не делают, и любое изменение формы данных задевает всю цепочку.

Прежде чем тянуться к Context, стоит вспомнить более дешёвый приём — передачу через children. Часто промежуточные компоненты вообще не обязаны знать о содержимом:

<Layout>
  <Sidebar><Menu theme={theme} /></Sidebar>
</Layout>

Тут Layout получает готовый элемент и просто ставит его в нужное место — цепочка исчезает без всякого контекста.

Context

Context передаёт значение вниз по дереву в обход промежуточных компонентов. Не «хранилище состояния» — именно способ доставки.

const ThemeContext = createContext("light");

function App() {
  const [theme, setTheme] = useState("light");
  return (
    <ThemeContext.Provider value={theme}>
      <Layout />
    </ThemeContext.Provider>
  );
}

function Item() {
  const theme = useContext(ThemeContext);   // берёт значение ближайшего Provider сверху
  …
}

Само состояние по-прежнему живёт в useState — Context только избавляет от передачи через промежуточные слои. Поэтому он не заменяет поднятие состояния, а дополняет его: сначала состояние поднимают, потом, если путь вниз слишком длинный, доставляют контекстом.

Цена контекста

При изменении значения перерисовываются все компоненты, которые его читают, — независимо от того, нужна ли им изменившаяся часть. Отсюда два практических правила.

Не класть в один контекст всё подряд. Если в объекте лежат и тема, и корзина, то смена темы перерисует всех, кто читает корзину. Лучше разные контексты для разных по частоте изменения данных.

Следить за ссылкой на объект. Вот частая ошибка:

<Ctx.Provider value={{ user, setUser }}>   // новый объект на каждый рендер

Литерал создаёт новый объект при каждом рендере провайдера, значение контекста «меняется» всегда, и все потребители перерисовываются впустую. Значение с несколькими полями заворачивают в useMemo:

const value = useMemo(() => ({ user, setUser }), [user]);

Для часто меняющихся данных — позиции курсора, значения поля ввода — Context плохой выбор: перерисовка всего поддерева на каждое нажатие клавиши заметна. Такие данные держат локально и поднимают ровно настолько, насколько нужно.

Ключи в списках

Тема соседняя, но ошибки даёт похожие. key нужен React, чтобы при следующем рендере понять, какой элемент какому соответствует.

Индекс массива в качестве ключа безопасен только для статичного списка. Как только элементы можно добавлять, удалять или сортировать, индексы съезжают: React решит, что изменилось содержимое существующих элементов, и состояние внутри них — раскрытые блоки, введённый текст, фокус — прилипнет не к тем строкам. Ключ должен быть стабильным идентификатором самих данных.

Обратная сторона того же механизма — полезный приём: смена key заставляет React выбросить старый компонент и смонтировать новый с чистым состоянием. Так сбрасывают форму при переходе к другому пользователю: <Form key={userId} />.

Что уносим с собой. Поднятие состояния — перенос значения в ближайшего общего родителя; данные идут вниз пропсами, события вверх колбэками. Context не хранит состояние, а доставляет его в обход промежуточных слоёв, и стоит он перерисовки всех потребителей — поэтому берётся для редко меняющихся данных, а значение-объект заворачивается в useMemo. Перед контекстом стоит попробовать передачу через children. Производное состояние не хранят, а вычисляют.
