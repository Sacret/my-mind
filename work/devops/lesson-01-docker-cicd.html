Docker и CI/CD: контейнеры, образы и путь кода до продакшена

Новая область. В продвинутом тесте вопрос про отличие Continuous Delivery от Continuous Integration был угадан, а про Docker-часть вопросов не было вовсе — хотя «что происходит после git push» должен понимать каждый, кто выкатывает код. Урок собирает две половины одной картины: как упаковать приложение (контейнеры) и как автоматически довозить изменения до пользователей (CI/CD).

Проблема «у меня работает»

Приложению нужны определённая версия Node, системные библиотеки, переменные окружения. На ноутбуке разработчика всё это есть, на сервере — нет или другое. Контейнеры решают проблему упаковкой: приложение и его окружение едут вместе.

Контейнер и образ

Образ (image) — неизменяемый шаблон: файловая система с приложением, зависимостями и командой запуска. Контейнер — запущенный экземпляр образа: изолированный процесс со своей файловой системой, сетью и лимитами.

Контейнер — не виртуальная машина. У VM своя гостевая ОС и ядро, она тяжёлая (гигабайты, минуты запуска). Контейнеры делят ядро хоста и изолируются средствами самой ОС (namespaces, cgroups), поэтому легковесны: мегабайты и секунды.

Dockerfile

Образ описывают рецептом, каждая инструкция создаёт слой:

FROM node:22-alpine          # базовый образ
WORKDIR /app
COPY package*.json ./
RUN npm ci                   # слой с зависимостями
COPY . .                     # исходники
CMD ["node", "server.js"]    # что запускать

Слои кэшируются: если ничего не изменилось, Docker берёт готовый слой. Поэтому порядок важен: сначала редко меняющиеся вещи (зависимости), потом часто меняющиеся (исходники). Если скопировать все файлы до npm ci, любая правка кода будет заново ставить зависимости.

Другие приёмы: многоэтапная сборка (собрать в одном образе, в финальный положить только результат — образ становится меньше), .dockerignore (не тащить node_modules и секреты), запуск не от root.

Данные и секреты. Файловая система контейнера временна — записанное внутрь исчезнет вместе с ним. Постоянные данные хранят в томах (volumes) или во внешней базе. Секреты не вшивают в образ: передают через переменные окружения или менеджер секретов при запуске.

Несколько контейнеров: Compose

Приложение редко бывает одно: веб, база, кэш. Docker Compose описывает их одним файлом и поднимает командой docker compose up. Для продакшена в масштабе используют оркестраторы, главный из которых — Kubernetes: он следит, чтобы нужное число копий работало, перезапускает упавшие, раскатывает обновления без простоя.

CI и CD

Continuous Integration (CI) — непрерывная интеграция: на каждый коммит или pull request автоматически собирается проект и прогоняются тесты, линтер и проверки типов. Смысл — ловить поломку сразу и часто, пока она мелкая, а не при слиянии месячных веток.

Continuous Delivery (CD) — непрерывная поставка: каждое изменение, прошедшее CI, автоматически доводится до состояния «готово к выпуску» — собранный артефакт лежит в реестре, выкладывается на тестовое окружение, а на продакшен идёт по нажатию кнопки. Continuous Deployment идёт дальше и выкатывает в продакшен сам, без ручного подтверждения.

git push → CI: сборка, тесты, линтер
         → образ собран и отправлен в реестр
         → деплой на staging, автотесты
         → продакшен (по кнопке — Delivery, автоматически — Deployment)

Безопасные выкатки

  • Rolling update — заменять копии по одной, чтобы сервис не останавливался.
  • Blue-green — держать два окружения, переключить трафик разом и при проблеме вернуть обратно.
  • Canary — сначала показать новую версию 1–5% пользователей и следить за метриками.
  • Feature flags — код выкачен, но функция выключена; включают постепенно и отключают без деплоя.
  • Откат — образ неизменяем, поэтому вернуться к прошлой версии — значит запустить предыдущий образ.
Что уносим с собой. Образ — неизменяемый шаблон, контейнер — его запущенный экземпляр; контейнеры делят ядро хоста и потому легче виртуальных машин. В Dockerfile редко меняющееся кладут выше — слои кэшируются. CI собирает и тестирует каждый коммит; Continuous Delivery доводит прошедшее до состояния «готово к выпуску», а Deployment выкатывает само. Безопасность выкаток обеспечивают canary, blue-green, флаги функций и быстрый откат.
