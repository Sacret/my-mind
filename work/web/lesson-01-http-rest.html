HTTP и REST: методы, коды, CORS

В тесте не сошлись два вопроса: какой метод не идемпотентен и что означает stateless. Обе темы кажутся теорией для собеседования, но именно из них растут практические решения — можно ли повторить запрос после таймаута и почему в консоли краснеет CORS.

Из чего состоит обмен

Запрос — это метод, путь, заголовки и (не всегда) тело. Ответ — код состояния, заголовки и тело.

POST /api/orders HTTP/1.1
Host: shop.example
Content-Type: application/json
Authorization: Bearer eyJhbG…

{"item": 42, "qty": 2}

──────────────────────────

HTTP/1.1 201 Created
Content-Type: application/json
Location: /api/orders/1001

{"id": 1001, "status": "new"}

Всё, что происходит между браузером и сервером, укладывается в эту форму: и загрузка страницы, и запрос из fetch, и картинка.

Методы и два их свойства

У методов есть два независимых свойства, которые постоянно путают.

Безопасный (safe) — не меняет состояние на сервере, только читает.

Идемпотентный — повторное выполнение того же запроса оставляет систему в том же состоянии, что и однократное. Речь именно о состоянии сервера, а не об одинаковом ответе.

МетодБезопасныйИдемпотентныйСмысл
GETдадапрочитать
HEADдадапрочитать только заголовки
PUTнетдазаменить ресурс целиком
DELETEнетдаудалить
PATCHнеткак правило нетизменить частично
POSTнетнетсоздать, выполнить действие

Разберём два места, где интуиция подводит.

DELETE идемпотентен, хотя кажется, что нет. Первый вызов DELETE /orders/1001 удаляет заказ и отвечает 204. Второй отвечает 404 — ответ другой, но состояние сервера то же самое: заказа нет. Идемпотентность про состояние, а не про код ответа.

POST не идемпотентен: каждый вызов создаёт новый заказ. Отправила форму дважды — два заказа. Именно поэтому браузер переспрашивает при обновлении страницы после отправки формы, а платёжные API требуют ключ идемпотентности — уникальную строку, по которой сервер узнаёт повтор и не проводит второй платёж.

PUT идемпотентен, потому что заменяет ресурс целиком: «пусть у заказа будет qty = 5» можно повторять сколько угодно. А PATCH вида «увеличь qty на 1» — нет.

Зачем это на практике. Запрос ушёл, ответ не вернулся — сеть моргнула. Повторять можно только идемпотентный запрос: GET, PUT, DELETE. Повтор POST вслепую способен создать дубль. По этой же причине автоматический retry в HTTP-клиентах по умолчанию включён только для идемпотентных методов.

Stateless

Это второе, что не сошлось в тесте. Stateless не означает, что сервер ничего не хранит — база данных на месте, заказы никуда не деваются.

Означает вот что: каждый запрос содержит всю информацию, необходимую для его обработки. Сервер не помнит контекст предыдущих запросов от того же клиента.

Сравни:

С состоянием:   → выбрать склад №3
                → показать товары        (сервер помнит: склад №3)

Stateless:      → GET /warehouses/3/items   (всё в самом запросе)

Что это даёт: любой из десяти серверов за балансировщиком может обработать любой запрос — им не нужно делиться памятью о сессиях. Отсюда горизонтальное масштабирование, простые перезапуски и предсказуемое поведение при сбое одной машины.

Токен авторизации в заголовке — как раз проявление этого принципа: клиент прикладывает удостоверение личности к каждому запросу, вместо того чтобы сервер помнил, кто он такой.

Коды ответов

Первая цифра задаёт класс, и по ней сразу понятно, чья это проблема.

КлассСмыслЧья зона ответственности
1xxинформацияслужебные, встречаются редко
2xxуспех—
3xxперенаправление—
4xxошибка клиентачинить на стороне клиента
5xxошибка серверачинить на стороне сервера

Те, что встречаются каждый день:

  • 200 OK — успех с телом ответа.
  • 201 Created — ресурс создан, обычно после POST; адрес нового ресурса в заголовке Location.
  • 204 No Content — успех без тела, типичный ответ на DELETE.
  • 301 против 302 — переезд навсегда против временного. 301 браузеры и поисковики кешируют жёстко, откатить трудно.
  • 304 Not Modified — «у тебя уже свежая копия», ответ на условный запрос с ETag.
  • 400 Bad Request — запрос сломан синтаксически, сервер его не понял.
  • 401 Unauthorized — ты не представилась: токена нет, он истёк или невалиден.
  • 403 Forbidden — представилась, но тебе нельзя. Повторная авторизация не поможет.
  • 404 Not Found — ресурса нет.
  • 409 Conflict — конфликт с текущим состоянием, например запись уже существует.
  • 422 Unprocessable Entity — синтаксис верный, но данные не проходят валидацию.
  • 429 Too Many Requests — превышен лимит частоты; в Retry-After сервер говорит, когда вернуться.
  • 500 Internal Server Error — сервер упал на своей стороне.
  • 502 Bad Gateway / 503 Service Unavailable / 504 Gateway Timeout — прокси не дозвался до приложения, сервис недоступен, вышел таймаут. Это диагноз инфраструктуры, а не кода.
Ловушка fetch. Промис из fetch отклоняется только при сетевой ошибке. Ответ 404 или 500 — это успешно доставленный ответ, и catch на него не сработает. Проверять нужно вручную: if (!res.ok) throw new Error(res.status).

REST в одном абзаце

REST — не протокол и не библиотека, а стиль проектирования API. Его суть: адресуемые ресурсы вместо действий, стандартные методы поверх них, stateless-обмен.

Не по REST:  POST /getUserById?id=7
             POST /deleteUser?id=7

По REST:     GET    /users/7
             DELETE /users/7
             GET    /users/7/orders?status=new

Существительные в пути, глаголы в методе, фильтры в query-параметрах. Практическая ценность не в чистоте идеи, а в предсказуемости: по адресу и методу понятно, что произойдёт, без чтения документации.

CORS: почему браузер ругается на чужой ответ

Здесь важно с самого начала уложить главное: запрос доходит до сервера, сервер его обрабатывает и отвечает — а браузер не отдаёт этот ответ твоему коду. CORS ничего не блокирует на сервере; это защита в браузере.

Причина — политика одного источника (same-origin policy). Источник — это тройка «схема + домен + порт». Всё, что отличается хотя бы одним элементом, — чужой источник:

https://app.example.com        исходная страница
http://app.example.com         другой источник (схема)
https://api.example.com        другой источник (поддомен)
https://app.example.com:8080   другой источник (порт)

Зачем это нужно: браузер автоматически прикладывает к запросам куки нужного домена. Без такой политики любой сайт мог бы из твоей вкладки дёрнуть банковское API — с твоими куками — и прочитать ответ.

Чтобы разрешить чтение, отвечать должен сервер, добавляя заголовок:

Access-Control-Allow-Origin: https://app.example.com

Простые запросы (GET, HEAD, простой POST без нестандартных заголовков) уходят сразу. Всё остальное — PUT, DELETE, POST с Content-Type: application/json, любой кастомный заголовок вроде Authorization — вызывает предварительный запрос (preflight):

OPTIONS /api/orders
Origin: https://app.example.com
Access-Control-Request-Method: DELETE
Access-Control-Request-Headers: authorization

  ↓

204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: authorization, content-type
Access-Control-Max-Age: 86400

Браузер сам спрашивает разрешение перед настоящим запросом. Max-Age говорит, сколько секунд помнить ответ, чтобы не спрашивать перед каждым вызовом.

Если нужны куки, условий сразу два и оба обязательны: клиент шлёт fetch(url, { credentials: "include" }), а сервер отвечает Access-Control-Allow-Credentials: true и обязательно конкретным источником — Access-Control-Allow-Origin: * вместе с куками не работает.

Как читать ошибку CORS. Она означает «сервер не разрешил моему источнику читать ответ» и чинится на сервере или на прокси. Правки во фронтенде помочь не могут — кроме варианта проксировать запрос через свой бэкенд, где политики одного источника просто нет. Отсюда и devServer proxy в сборщиках: он делает адрес API своим.
Что уносим с собой. Идемпотентность — про состояние сервера при повторе: GET, PUT, DELETE идемпотентны, POST нет, поэтому повторять вслепую можно только первые. Stateless — каждый запрос самодостаточен, а не «сервер ничего не хранит». 401 — не представилась, 403 — нельзя. fetch не бросает исключение на 4xx и 5xx. CORS решается заголовками сервера, запрос до него доходит в любом случае.
