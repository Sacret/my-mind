Отзывчивость интерфейса: INP, долгие задачи и главный поток

Закрывает провал продвинутого теста: какая метрика Core Web Vitals с 2024 года отвечает за отзывчивость. Ответ — INP, и он заменил FID. Скорость загрузки — это только полдела: страница может открыться мгновенно и при этом «залипать» при каждом клике. Урок про то, почему это происходит и как лечится.

Три метрики Core Web Vitals

МетрикаЧто измеряетХорошо
LCP — Largest Contentful Paintкогда появился самый крупный видимый элемент — обычно картинка или заголовокдо 2,5 с
INP — Interaction to Next Paintотзывчивость: сколько проходит от действия пользователя до следующего обновления экранадо 200 мс
CLS — Cumulative Layout Shiftстабильность: насколько элементы «прыгают» при загрузкедо 0,1

В марте 2024 года INP заменил FID (First Input Delay). FID мерил только задержку до начала обработки самого первого клика. INP учитывает все взаимодействия за визит — клики, касания, нажатия клавиш — и берёт почти худшее из них, а измеряет полный путь: задержку до обработчика, время самого обработчика и отрисовку результата.

Главный поток — узкое место

Почти вся работа страницы — разбор HTML, стили, раскладка, отрисовка и исполнение JS — идёт в одном главном потоке. Пока он занят, браузер не может ответить на клик: нажатие ждёт своей очереди. Пользователь видит зависший интерфейс.

Долгой задачей (long task) называют работу на главном потоке дольше 50 мс: всё, что превышает, заметно ощущается как задержка. Найти такие задачи можно в Performance-панели DevTools — они помечены красным углом.

button.addEventListener("click", () => {
  const result = heavySort(bigArray);   // 400 мс — интерфейс мёртв
  render(result);
});

Как чинить

1. Отдать браузеру дышать: разбить работу

Длинную задачу режут на куски и между ними уступают поток: браузер успевает обработать клики и отрисовать кадр. Инструменты — setTimeout(0), requestIdleCallback, а в новых браузерах scheduler.yield().

async function processAll(items) {
  for (const chunk of chunks(items, 100)) {
    process(chunk);
    await scheduler.yield();   // вернуть управление браузеру
  }
}

2. Вынести в Web Worker

Web Worker — отдельный поток для вычислений: сортировка больших массивов, разбор данных, обработка изображений. У воркера нет доступа к DOM, обмен идёт сообщениями postMessage. Главный поток остаётся свободным.

3. Сделать меньше работы

  • Меньше JS. Каждый килобайт надо скачать, разобрать и выполнить: лишние библиотеки, полифилы, аналитика.
  • Debounce и throttle для частых событий: scroll, input, resize.
  • Мемоизация и виртуализация списков — не рисовать 10 000 строк, когда видно 20.
  • Не вызывать принудительный layout. Чтение offsetHeight сразу после записи стиля заставляет браузер пересчитать раскладку немедленно; группируйте чтения и записи.

Быстрая реакция — не значит быстрый результат. INP учитывает следующий кадр после клика, а не завершение всей работы. Если обработчик тяжёл, покажите мгновенный отклик (спиннер, состояние кнопки), а тяжёлое сделайте после отрисовки.

Как измерять

Лабораторные данные (Lighthouse, DevTools) воспроизводимы, но искусственны. Полевые (RUM, CrUX, библиотека web-vitals) собирают метрики у реальных пользователей — на слабых телефонах и плохой сети. INP по-настоящему виден только в поле, так как зависит от того, что пользователь реально делает. Поэтому проверять надо и там, и там.

Что уносим с собой. Core Web Vitals: LCP — загрузка, INP — отзывчивость, CLS — стабильность. INP заменил FID в 2024 году и учитывает все взаимодействия целиком. Главный поток один, а задача дольше 50 мс — «долгая». Лечат разбиением работы, Web Worker и сокращением JS; измерять стоит и в лаборатории, и в поле.
