Транзакции, уровни изоляции и проблема N+1

Закрывает вопросы продвинутого теста про READ COMMITTED и N+1 — оба отвечены наугад. SQL-урок научил делать запросы; здесь — как база держит данные целыми, когда одновременно работают сотни клиентов, и почему приложение с ORM вдруг делает тысячу запросов вместо одного.

Транзакция и свойства ACID

Транзакция — группа операций, которая выполняется как одно целое: либо все, либо ни одной. Классический пример — перевод денег: списать с одного счёта и зачислить на другой. Если после первого шага случится сбой, деньги не должны потеряться.

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;      -- или ROLLBACK при ошибке

Надёжные базы гарантируют четыре свойства (ACID):

  • Atomicity — атомарность: всё или ничего.
  • Consistency — согласованность: данные остаются в допустимом состоянии, ограничения соблюдены.
  • Isolation — изоляция: параллельные транзакции не мешают друг другу.
  • Durability — долговечность: подтверждённое не пропадёт даже при отключении питания.

Что ломается без изоляции

Когда транзакции идут одновременно, возможны аномалии:

АномалияЧто происходит
Грязное чтениечитаешь данные, которые другая транзакция ещё не подтвердила и, возможно, откатит
Неповторяющееся чтениедважды читаешь одну строку в транзакции и получаешь разные значения — между чтениями другая транзакция изменила и подтвердила
Фантомное чтениеповторный запрос по условию возвращает другие наборы строк — другая транзакция добавила или удалила подходящие

Уровни изоляции

Строже изоляция — меньше аномалий, но медленнее и больше блокировок. Стандарт SQL описывает четыре уровня:

УровеньГрязноеНеповторяющеесяФантомы
READ UNCOMMITTEDвозможновозможновозможны
READ COMMITTEDнетвозможновозможны
REPEATABLE READнетнетвозможны (в PostgreSQL нет)
SERIALIZABLEнетнетнет

READ COMMITTED — уровень по умолчанию в PostgreSQL и многих других: видны только подтверждённые данные, поэтому от грязного чтения защищает, но от неповторяющегося — нет: между двумя запросами чужой COMMIT может изменить строку. SERIALIZABLE даёт иллюзию, что транзакции идут по одной, но вынуждает повторять транзакции при конфликтах.

Блокировки и дедлоки. Если две транзакции ждут друг друга (первая держит строку 1 и хочет 2, вторая наоборот), возникает взаимная блокировка. База обнаружит её и отменит одну из транзакций — приложение должно уметь повторить. Помогает единый порядок обращения к строкам и короткие транзакции.

Проблема N+1

Самая частая причина медленных страниц при работе через ORM. Нужен список из 100 постов с автором каждого:

const posts = await Post.findAll();          // 1 запрос: все посты
for (const post of posts) {
  post.author = await User.findById(post.authorId);  // +100 запросов
}

Итого 1 запрос за списком и ещё N — по одному на каждую запись: 101 запрос вместо двух. Каждый — сетевой круг до базы, и задержка растёт линейно с длиной списка. На разработке с десятью записями это незаметно, на проде с тысячей — катастрофа.

Лечение:

  • JOIN — одним запросом получить посты вместе с авторами.
  • Eager loading — попросить ORM сразу подгрузить связь: include, select_related, with.
  • Пакетная загрузка — второй запрос WHERE id IN (...) для всех нужных авторов сразу (так работает DataLoader в GraphQL).

Обнаруживается подсчётом запросов на запрос: если число растёт вместе с данными — это N+1.

Что уносим с собой. Транзакция — всё или ничего; ACID — атомарность, согласованность, изоляция, долговечность. READ COMMITTED защищает от грязного чтения, но не от неповторяющегося; SERIALIZABLE закрывает всё ценой скорости. Дедлоки лечат единым порядком обращения и повтором. N+1 — один запрос за списком и N за связанными записями; лечится JOIN, eager loading или пакетной загрузкой.
