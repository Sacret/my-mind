Отладка: как искать причину, а не симптом

Отладка кажется делом интуиции: смотришь на код, пока не увидишь ошибку. На самом деле это процедура с понятными шагами, и разница между часом и тремя днями поиска — почти всегда в том, соблюдался ли порядок. Урок про этот порядок и про инструменты, которые сокращают перебор.

Порядок работы

  1. Воспроизвести. Пока баг не воспроизводится по команде, чинить нечего: не будет ясно, помогло ли исправление.
  2. Сформулировать гипотезу — одно проверяемое утверждение: «в это поле приходит строка вместо числа».
  3. Проверить её так, чтобы получить ответ «да» или «нет», а не «вроде теперь работает».
  4. Сузить область вдвое и повторить.
  5. Починив, объяснить, почему баг вообще возник. Исправление, которое непонятно почему работает, — не исправление.

Главная ловушка. Менять несколько вещей сразу. Если после трёх правок заработало, неизвестно, что помогло, — и вернуть остальные две нельзя, потому что вдруг дело в них.

Воспроизведение и минимальный пример

«Иногда падает у пользователя» — не воспроизведение. Нужно довести до последовательности шагов, которая ломает всё каждый раз: конкретные данные, конкретный размер окна, конкретный порядок действий.

Дальше пример сокращают: убирают всё, без чего баг остаётся. Часто на середине этой процедуры причина становится очевидной сама — «падает, только если массив пустой». Заодно получается готовый тест.

Отдельная категория — баг, воспроизводимый только в проде. Тогда сначала ищут различие: версия сборки, переменные окружения, данные, права, часовой пояс, кэш CDN.

Половинное деление

Самый сильный приём отладки — тот же, что в бинарном поиске: каждый шаг должен уполовинивать область поиска, а не проверять по одному кандидату.

  • По коду: проверка в середине пути — данные испорчены уже здесь или ещё нет? Дальше половина отпадает.
  • По данным: падает на файле из 10 000 строк — оставить 5000, потом 2500. Обычно виноваты две-три строки.
  • По конфигурации: отключить половину плагинов, расширений браузера, флагов.
  • По истории: найти коммит, который всё сломал.

git bisect

git bisect start
git bisect bad                 # сейчас сломано
git bisect good v1.4.0         # на этой версии работало
# git выдаёт коммит посередине, проверяешь и отвечаешь:
git bisect good | git bisect bad
git bisect reset               # выйти и вернуться на исходную ветку

За примерно log₂ n шагов находится коммит, сломавший поведение: из тысячи коммитов — около десяти проверок. Если проверку можно автоматизировать, всё делается одной командой: git bisect run npm test — скрипт должен возвращать нулевой код для «хорошо» и ненулевой для «плохо».

Точки останова против console.log

Логи — нормальный инструмент, но у отладчика есть то, чего в логах нет: состояние в момент паузы целиком, включая переменные всех вызывающих функций в стеке.

ВозможностьЗачем
Условная точка остановаостановиться только когда id === 42 — вместо тысячи срабатываний
Logpointпечатать значение без остановки и без правки кода
Точка на исключении«Pause on exceptions» — пауза ровно там, где брошена ошибка, в том числе перехваченная
Стек вызововувидеть, кто вызвал функцию с плохим аргументом — обычно там и причина
Точка на изменении DOMпоймать код, который меняет узел или его атрибуты

Ловушка консоли. console.log(obj) печатает ссылку: раскрыв объект в консоли позже, видишь его текущее состояние, а не то, что было в момент вызова. Для снимка — console.log(structuredClone(obj)) или JSON.stringify.

Полезные мелочи: console.table для массивов объектов, console.count вместо счётчика вручную, console.trace для стека без остановки, группировка через console.group.

Читать ошибку целиком

Стек вызовов читают сверху вниз: первая строка — место, где ошибка брошена, ниже — кто это вызвал. Свои файлы в стеке важнее строк из библиотек: обычно виноват аргумент, который туда передали.

Если стек ведёт в минифицированный код, нужны source maps. Отладка по a.b(c) из собранного бандла — потерянное время.

В браузере одинаково полезны три вкладки: Console (ошибка), Network (что на самом деле ушло и что вернулось — статус, заголовки, тело), Application (куки, хранилище, кэш). Много «багов фронтенда» оказываются ответом сервера, который никто не открыл.

Когда «этого не может быть»

Такое ощущение — почти всегда признак ложного предположения. Что проверяют первым делом:

  • Выполняется ли вообще этот код? Поставить заведомую отметку и убедиться, что она видна.
  • Та ли это версия? Пересобрано, кэш браузера сброшен, нужная ветка, нужный сервер, нужная база.
  • Те ли данные? Не тестовый ли аккаунт, не старая ли запись в кэше, не пустой ли ответ.
  • Тот ли файл открыт? Дубликат модуля, копия компонента, правка в собранной папке вместо исходников.

Хайзенбаг — баг, исчезающий при попытке его наблюдать. Обычно это гонка: добавленное логирование меняет тайминг, и порядок событий становится другим. Ищут не логами, а рассуждением о порядке: кто на что не дождался, что выполнилось дважды, где нет отмены предыдущего запроса.

Дисциплина, которая экономит часы

  • Записывать проверенное. Список гипотез и результатов не даёт по третьему разу проверять одно и то же.
  • Резиновая уточка. Объяснение вслух — способ обнаружить недоказанное предположение в собственных рассуждениях.
  • Тест на баг. Сначала падающий тест, потом исправление: подтверждает диагноз и страхует от возвращения.
  • Поискать тот же класс ошибок в других местах. Забытая проверка на null редко бывает в единственном экземпляре.
  • Сделать баг заметнее в следующий раз: понятное сообщение об ошибке, проверка входных данных на границе, лог с идентификатором запроса.
Что уносим с собой. Порядок: воспроизвести → гипотеза → проверка → сузить вдвое → объяснить причину. Менять по одной вещи за раз. Минимальный пример часто сам показывает причину. Половинное деление работает по коду, данным, конфигурации и истории — последнее делает git bisect за log₂ n шагов. Отладчик даёт состояние и стек целиком; console.log(obj) печатает ссылку, для снимка нужен клон. «Не может быть» означает ложное предположение: тот ли код, версия, данные. Хайзенбаг — обычно гонка.
