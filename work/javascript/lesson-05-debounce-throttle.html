debounce и throttle

Вопрос #25 входного теста был провален: варианты «не чаще раза в N мс» и «отложить до паузы» — это два разных приёма, и в тесте они стояли рядом. Разница между ними ровно в одном: что считать поводом для вызова — паузу или истёкший интервал. Из этого выводится всё остальное, включая выбор в конкретной задаче.

Задача

Некоторые события приходят пачками: ввод текста, движение мыши, прокрутка, изменение размера окна. Обработчик на каждое из них — это сотни вызовов в секунду, и если внутри запрос к серверу или перерасчёт разметки, интерфейс встаёт.

Два способа сократить число вызовов:

debounce

Каждое новое событие отменяет запланированный вызов и планирует новый. Вызов происходит, только если событий не было N мс.

function debounce(fn, ms) {
  let timer;
  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), ms);
  };
}

Три детали, без которых реализация неполная:

  • clearTimeout первым делом — иначе таймеры накапливаются.
  • fn.apply(this, args), а не fn() — иначе теряются аргументы и контекст. Обёртка не должна быть стрелочной, иначе this возьмётся из внешней области.
  • Вызывается последний набор аргументов — обычно это и нужно: важен итоговый текст в поле, а не промежуточный.

Где применять

  • Поиск-подсказка при вводе: запрос уходит, когда пользователь остановился.
  • Автосохранение черновика.
  • Валидация формы по завершении ввода.
  • resize, когда нужен только итоговый размер окна.
Где debounce неуместен. Там, где нужна обратная связь во время действия: индикатор прокрутки, перетаскивание, отрисовка при движении мыши. При непрерывном потоке событий debounce не вызовется ни разу, и интерфейс будет выглядеть замершим.

throttle

Вызов проходит не чаще одного раза в N мс, остальные отбрасываются.

function throttle(fn, ms) {
  let last = 0;
  let timer = null;
  return function (...args) {
    const now = Date.now();
    const rest = ms - (now - last);
    if (rest <= 0) {                       // интервал истёк — вызываем сразу
      clearTimeout(timer);
      timer = null;
      last = now;
      fn.apply(this, args);
    } else if (!timer) {                   // хвостовой вызов: не терять последнее событие
      timer = setTimeout(() => {
        last = Date.now();
        timer = null;
        fn.apply(this, args);
      }, rest);
    }
  };
}

Здесь важны два края интервала:

  • Leading — вызов на первом событии, немедленно. Без него интерфейс реагирует с задержкой на самое первое действие.
  • Trailing — вызов в конце интервала, чтобы не потерять последнее событие. Без него финальное положение прокрутки может не примениться.

Наивная версия «просто с флагом» обычно теряет trailing — и это самый частый дефект самописного throttle.

Где применять

  • Обработка scroll: подсветка активного раздела, «показать кнопку наверх».
  • Отрисовка при движении мыши и перетаскивании.
  • Ограничение частоты обращений к API.
  • Отправка позиции курсора в совместном редакторе.

Как выбирать

Один вопрос: нужен ли результат промежуточных событий?

  • Нужен только итог, а промежуточные вызовы — расход впустую → debounce.
  • Нужна регулярная реакция по ходу действия → throttle.

Типичные интервалы: 200–500 мс для поиска по вводу, 100–300 мс для прокрутки и мыши, 16 мс — если задача чисто визуальная, но тогда обычно лучше requestAnimationFrame.

Про rAF. Для перерисовки лучше не throttle по времени, а requestAnimationFrame: браузер сам вызовет колбэк перед следующим кадром и не станет вызывать его во вкладке в фоне. throttle на 16 мс этой синхронизации не даёт.

Подводные камни в React

Функция, созданная прямо в теле компонента, пересоздаётся на каждом рендере — вместе с внутренним таймером. Получается новая обёртка без памяти о предыдущей, и приём перестаёт работать вовсе:

// сломано: новый debounce на каждый рендер
const onChange = debounce(save, 500);

// правильно: обёртка создаётся один раз
const onChange = useMemo(() => debounce(save, 500), []);

useEffect(() => () => onChange.cancel?.(), [onChange]);  // отмена при размонтировании

Отсюда же требование к практичной реализации: у обёртки должен быть метод cancel. Иначе отложенный вызов сработает после размонтирования компонента и обратится к тому, чего уже нет.

Смежные приёмы

  • Отмена устаревших запросов. debounce сокращает число запросов, но не спасает от гонки: ответ на старый запрос может прийти после нового. Нужен AbortController или проверка актуальности ответа.
  • Мемоизация — не про частоту, а про повторные вызовы с теми же аргументами; их часто путают в вопросах на собеседовании.
  • Батчинг — накопить события и отправить пачкой; полезнее debounce там, где терять промежуточные данные нельзя.
Что уносим с собой. debounce откладывает вызов до паузы в N мс и при непрерывном потоке не вызывается вовсе. throttle пропускает не чаще одного вызова в N мс и работает равномерно. Нужен итог — debounce, нужна реакция по ходу — throttle. Не терять trailing-вызов, передавать args и this, иметь cancel. В React создавать обёртку один раз через useMemo. Для визуальных задач — requestAnimationFrame.
