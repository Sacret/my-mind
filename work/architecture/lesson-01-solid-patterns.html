Архитектура: SOLID, паттерны, чистая архитектура и микросервисы

Новая область. В продвинутом тесте четыре вопроса про архитектуру — «открыт/закрыт», Observer, микросервисы и направление зависимостей — были отвечены верно, но все наугад. Архитектура — не про модные схемы, а про одну задачу: сделать так, чтобы код можно было менять дёшево. Все принципы этого урока — способы ограничить, сколько мест ломается от одного изменения.

SOLID: пять принципов

БукваПринципСуть
SSingle Responsibilityу модуля одна причина для изменения
OOpen/Closedоткрыт для расширения, закрыт для изменения
LLiskov Substitutionнаследника можно подставить вместо родителя, не сломав поведение
IInterface Segregationмного узких интерфейсов лучше одного широкого
DDependency Inversionвысокий уровень не зависит от низкого; оба — от абстракции

Самый показательный — O. Новое поведение добавляется новым кодом, а не правкой старого. Вместо цепочки if (type === "card") … else if (type === "paypal") …, которую приходится дописывать при каждом способе оплаты, — общий интерфейс и по классу на способ:

class Card   { pay(sum) { … } }
class PayPal { pay(sum) { … } }

function checkout(method, sum) { method.pay(sum); }   // не меняется

Новый способ оплаты — новый класс, а checkout остаётся нетронутым. Принципы — не догма: применять их стоит, когда изменения действительно повторяются, иначе получается избыточная сложность.

Паттерны проектирования

Паттерн — проверенное решение типовой проблемы, имя которого понятно коллегам без объяснений. Три группы: порождающие (как создавать объекты), структурные (как объединять) и поведенческие (как взаимодействуют). Часто встречаются:

  • Observer (Наблюдатель) — объект хранит список подписчиков и сам уведомляет их об изменении. На нём построены DOM-события, addEventListener, Redux-подписки, RxJS.
  • Strategy — взаимозаменяемые алгоритмы за общим интерфейсом (те самые способы оплаты).
  • Factory — создание объектов спрятано за функцией, вызывающая сторона не знает конкретного класса.
  • Adapter — обёртка, приводящая чужой интерфейс к нужному; так подключают сторонние библиотеки.
  • Decorator — добавляет поведение обёрткой, не меняя исходный объект (middleware, HOC).

Слоистая и чистая архитектура

Идея: разделить код на слои с чёткими ролями — интерфейс (UI, HTTP), приложение (сценарии), домен (бизнес-правила), инфраструктура (база, внешние API). В чистой (луковой, гексагональной) архитектуре слои изображают кольцами, а главное правило — зависимости направлены снаружи внутрь: UI и база зависят от домена, а не наоборот.

Домен ничего не знает о фреймворке, базе или интерфейсе: он описывает правила («заказ нельзя оформить без товаров»), а внешние детали подключаются через интерфейсы. Итог: бизнес-логику можно тестировать без базы, а PostgreSQL заменить другой базой, не трогая правил. Это и есть инверсия зависимостей — буква D.

Монолит и микросервисы

МонолитМикросервисы
Устройствоодно приложение, одно развёртываниемного небольших сервисов, каждый со своей базой и релизом
Плюсыпросто писать, отлаживать, деплоить; вызовы внутри процесса быстрые и надёжныенезависимые команды и релизы; масштабирование по частям; изоляция сбоев
Минусырастёт связность; любая правка требует деплоя всегосеть между сервисами: задержки, частичные отказы, распределённые данные

Плата за микросервисы — распределённая система: вызов, который раньше был функцией, теперь идёт по сети и может тормозить, падать или прийти дважды. Нужны таймауты, повторы, идемпотентность, трассировка запросов, согласованность данных без общей транзакции. Поэтому разумная тактика — начинать с аккуратного модульного монолита и выделять сервисы, когда для этого появилась настоящая причина.

Что уносим с собой. SOLID сокращает связность: O — расширять новым кодом, D — зависеть от абстракций. Observer — объект уведомляет своих подписчиков; Strategy, Factory, Adapter — типовые решения. В чистой архитектуре зависимости направлены внутрь, к домену. Микросервисы покупают независимость ценой сети: задержек, частичных отказов и распределённых данных.
