Node.js: один поток, цикл событий и как не заблокировать сервер

Новая область. В продвинутом тесте вопрос про то, почему синхронный расчёт останавливает весь сервер, был угадан. Node.js — тот же JavaScript и тот же цикл событий, но применённые к серверу, где на одном процессе одновременно живут тысячи клиентов. Это одновременно его сила и самая частая ловушка.

Что такое Node.js

Node — среда выполнения JavaScript вне браузера, построенная на движке V8 и библиотеке libuv, которая делает неблокирующий ввод-вывод. У Node нет DOM и window, зато есть файлы, сеть, процессы. Модель: код JS выполняется в одном потоке, а всё медленное (сеть, диск, DNS) делегируется системе и возвращается коллбэком или промисом.

Цикл событий на сервере

Урок про event loop в браузере описывал очередь макро- и микрозадач. В Node устройство то же, но с фазами: таймеры, ожидающие коллбэки I/O, опрос новых событий, setImmediate, закрытие. Микрозадачи (промисы, process.nextTick) разбираются между фазами.

console.log("1");
setTimeout(() => console.log("2"), 0);
setImmediate(() => console.log("3"));
Promise.resolve().then(() => console.log("4"));
process.nextTick(() => console.log("5"));
// 1, 5, 4, затем 2 и 3 (порядок 2 и 3 из главного модуля не гарантирован)

process.nextTick срабатывает раньше промисов — раньше любой микрозадачи. Злоупотребление им может «голодом» задушить ввод-вывод.

Почему один поток выдерживает тысячи клиентов

Типичный запрос почти не считает, а ждёт: ответа базы, файла, другого сервиса. Пока он ждёт, поток свободно берётся за другие запросы. Одна нить успевает обслуживать тысячи соединений, потому что ожидание не занимает процессор. Такая модель идеальна для I/O-нагрузки: API, прокси, чаты, стриминг.

app.get("/users/:id", async (req, res) => {
  const user = await db.find(req.params.id);   // ждём — поток свободен
  res.json(user);
});

Ловушка: блокировка цикла

Оборотная сторона: тяжёлая синхронная работа занимает единственный поток, и цикл событий не может взять ни одного нового запроса, пока она не закончится. Пока один клиент ждёт расчёта, остальные «подвисают».

app.get("/report", (req, res) => {
  const result = heavyLoop(1e10);   // 8 секунд — сервер молчит для всех
  res.json(result);
});

Классические виновники: fs.readFileSync в обработчике, большие циклы, JSON.parse огромной строки, сложные регулярные выражения с катастрофическим возвратом, шифрование и сжатие «в лоб», синхронные версии методов (*Sync).

Способы лечения:

  • Worker threads — отдельные потоки для CPU-нагрузки, обмен сообщениями.
  • Дочерние процессы и кластер (cluster, PM2, контейнеры): несколько процессов Node на разных ядрах, балансировщик раздаёт клиентов.
  • Очередь задач — тяжёлое кладут в очередь (Bull, RabbitMQ), а обрабатывает отдельный воркер.
  • Разбиение на куски с уступкой цикла через setImmediate.

«Node не годится для вычислений». Это упрощение. Тяжёлые вычисления в основном потоке вредны, но вынесенные в worker или отдельный сервис они не мешают серверу. Главное — знать, что в потоке JS занимает время.

Потоки (streams)

Файл на два гигабайта нельзя целиком прочитать в память. Stream обрабатывает данные кусками: читаешь чанк, передаёшь дальше, забываешь. Виды — Readable, Writable, Duplex, Transform. Метод pipe (или pipeline) соединяет их и заодно управляет обратным давлением: если получатель не успевает, отправитель притормаживается.

const { pipeline } = require("node:stream/promises");
await pipeline(
  fs.createReadStream("big.log"),
  zlib.createGzip(),
  fs.createWriteStream("big.log.gz")
);   // память постоянна, файл любого размера

Так работают отдача больших файлов, обработка загрузок, стриминг видео, сжатие на лету.

Обработка ошибок и завершение

  • Необработанный отказ промиса или исключение в асинхронном коде роняет процесс (в современных версиях) — ставьте общий обработчик и логируйте.
  • При остановке не рвите соединения: ловите SIGTERM, перестаньте принимать новые запросы, закончите текущие и выйдите (graceful shutdown).
Что уносим с собой. Node — JS на V8 и libuv; код выполняется в одном потоке, а медленный ввод-вывод уходит в систему. Поэтому один процесс держит тысячи ждущих клиентов. Тяжёлая синхронная работа блокирует цикл событий и останавливает весь сервер: её выносят в worker threads, процессы или очередь. Потоки данных читают и пишут кусками с обратным давлением, а process.nextTick срабатывает раньше промисов.
