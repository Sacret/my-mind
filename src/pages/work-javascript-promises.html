Промисы: all, allSettled, race и async/await

Вопрос #23 про Promise.allSettled был отмечен «угадала». Урок про event loop объяснил, когда выполняется отложенный код. Этот — про то, чем его принято выражать: какие есть комбинаторы, где async/await молча теряет ошибки и почему последовательный await в цикле бывает в разы медленнее нужного.

Промис — это значение, которого пока нет

У промиса три состояния: pending, затем ровно один переход — либо в fulfilled со значением, либо в rejected с причиной. Переход необратим, повторные вызовы resolve или reject игнорируются.

Два свойства, из которых следует почти всё остальное:

  • Промис запускает работу сразу при создании, а не при вызове .then. Функция внутри new Promise выполняется синхронно.
  • Обработчики всегда асинхронны. Даже у уже разрешённого промиса .then попадёт в очередь микрозадач, а не выполнится тут же.
console.log("A");
Promise.resolve().then(() => console.log("B"));
console.log("C");
// A C B — даже при готовом значении then ждёт микрозадачу

Четыре комбинатора

Разница между ними — единственное, что нужно помнить твёрдо.

МетодРазрешаетсяОтклоняетсяРезультат
allкогда выполнены всена первой же ошибкемассив значений
allSettledкогда все завершились любым образомникогдамассив {status, value|reason}
raceна первом завершившемся — успех или ошибкаего значение или ошибка
anyна первом успешномесли провалились всепервое значение

all — fail-fast

const [user, posts] = await Promise.all([fetchUser(), fetchPosts()]);

Запросы идут параллельно, общее время равно самому долгому. Но первая же ошибка отклоняет весь Promise.all, и результаты успевших получить нельзя — они потеряны. При этом остальные запросы не отменяются: они продолжают выполняться, просто их результат уже некуда деть.

allSettled — нужны все ответы

const results = await Promise.allSettled([a(), b(), c()]);

const ok   = results.filter(r => r.status === "fulfilled").map(r => r.value);
const bad  = results.filter(r => r.status === "rejected").map(r => r.reason);

Подходит там, где частичный результат имеет смысл: загрузка виджетов на дашборде, пакетная отправка, опрос нескольких источников. allSettled не отклоняется никогда — соответственно, catch после него не сработает, и статус каждого элемента нужно проверять вручную.

race и any

race реагирует на первое завершение, включая ошибку. Типичное применение — таймаут:

const withTimeout = (p, ms) => Promise.race([
  p,
  new Promise((_, rej) => setTimeout(() => rej(new Error("timeout")), ms))
]);

any реагирует на первый успех и игнорирует ошибки, пока есть надежда: запрос к нескольким зеркалам, где нужен любой ответивший. Если провалились все, он отклоняется с AggregateError, в котором лежит массив причин.

Частая ошибка выбора. Взять race там, где нужен any: первый же упавший запрос завалит всю конструкцию, хотя остальные зеркала ответили бы нормально.

async/await

async-функция всегда возвращает промис, даже если внутри обычный return 1. await ждёт разрешения и разворачивает значение, а при отклонении бросает исключение — поэтому обработка ошибок становится обычным try/catch.

async function load(id) {
  try {
    const res = await fetch(`/api/items/${id}`);
    if (!res.ok) throw new Error(`HTTP ${res.status}`);   // fetch НЕ падает на 404
    return await res.json();
  } catch (e) {
    log(e);
    throw e;              // проглотить или пробросить — но решить осознанно
  }
}

Главная ошибка производительности

// последовательно: сумма всех задержек
for (const id of ids) {
  results.push(await fetchItem(id));
}

// параллельно: время самого долгого
const results = await Promise.all(ids.map(id => fetchItem(id)));

В первом варианте каждый следующий запрос ждёт предыдущий. Для десяти запросов по 300 мс это 3 секунды против 300 мс. Последовательный await оправдан, только когда следующий шаг зависит от предыдущего.

Про forEach. arr.forEach(async x => { await f(x) }) не ждёт ничего: forEach игнорирует возвращаемые промисы и завершается мгновенно. Нужен for...of с await или Promise.all(arr.map(...)).

Тихая потеря ошибок

Три способа потерять ошибку, все встречаются в реальном коде:

  • Забытый await. doWork() без await внутри try/catch — исключение возникнет позже, когда блок уже покинут, и превратится в необработанное отклонение.
  • Промис создан, но нигде не обработан. Отклонение всплывает как unhandledrejection и в Node по умолчанию гасит процесс.
  • return вместо return await внутри try. При return p функция возвращает промис до его разрешения, и catch этой же функции ошибку уже не поймает.
try {
  return getData();        // ошибка НЕ попадёт в catch ниже
  // return await getData(); ← поймается
} catch (e) { handle(e); }

Порядок выполнения

Связь с уроком про event loop: каждый await — это микрозадача, код после него продолжается не сразу.

async function f() {
  console.log("1");
  await null;              // await любого значения тоже даёт микрозадачу
  console.log("3");
}
f();
console.log("2");
// 1 2 3

До первого await тело async-функции выполняется синхронно — это часто удивляет.

Практические правила

  • Независимые операции — Promise.all, зависимые — последовательный await.
  • Нужны все ответы вместе с ошибками — allSettled и разбор статусов.
  • Нужен любой успешный — any, нужен первый завершившийся — race.
  • Смешивать .then и await в одной функции не стоит: порядок становится трудно читаемым.
  • Отмену промис не поддерживает — для этого нужен AbortController, который передаётся в fetch сигналом.
Что уносим с собой. Промис стартует при создании, обработчики всегда через микрозадачу. all падает на первой ошибке, allSettled не падает никогда, race ждёт первого завершения, any — первого успеха. async-функция всегда возвращает промис. await в цикле последователен — это главная причина медленного кода. return без await внутри try теряет ошибку.
