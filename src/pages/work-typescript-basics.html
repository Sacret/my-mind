TypeScript: структурная типизация, сужение, дженерики

TypeScript ощущается как «JavaScript, в котором заставляют писать типы». На деле это отдельный инструмент со своей логикой: типы существуют только до сборки, совместимость определяется формой объекта, а главная работа — не расставить аннотации, а сузить широкий тип до конкретного там, где это нужно.

Типов нет в рантайме

Компилятор проверяет код и стирает все типы. На выходе — обычный JavaScript: ни одной аннотации, ни одного интерфейса. Отсюда следствия, о которые спотыкаются все:

interface User { id: number; name: string }

// так нельзя: интерфейса в рантайме не существует
if (x instanceof User) { … }        // ошибка компиляции

const data = await res.json();      // тип any — сервер мог прислать что угодно
const user = data as User;          // «as» ничего не проверяет, только затыкает компилятор

as — это не приведение и не проверка, а обещание компилятору: «поверь, тут User». Если сервер прислал другое, программа упадёт в рантайме ровно так же, как на чистом JS.

Правило границы. Всё, что приходит извне — ответ сервера, localStorage, параметры URL, — типизировать как unknown и разбирать проверками (руками или схемой вроде Zod). Внутри программы типам можно верить, на границе — нельзя.

Структурная типизация: важна форма, а не имя

В большинстве языков типы номинальные: Point совместим с Point, потому что так назван. В TypeScript типизация структурная — совместимость определяется набором полей:

interface Point { x: number; y: number }
interface Vector { x: number; y: number }

const v: Vector = { x: 1, y: 2 };
const p: Point = v;                 // ок: форма совпадает, имена не важны

function len(p: Point) { … }
len({ x: 1, y: 2 });                // ок
len({ x: 1, y: 2, z: 3 });          // ошибка при литерале, но…
const obj = { x: 1, y: 2, z: 3 };
len(obj);                           // …ок: лишние поля через переменную допустимы

Лишние поля запрещены только для объектного литерала прямо в вызове — это отдельная проверка на опечатки. Через переменную объект с лишними полями проходит: он ведь и правда содержит всё, что требуется.

Один any тихо выключает проверку в целой ветке программы: всё, что из него получено, тоже становится any. unknown — честная замена: он ничего не разрешает, пока тип не доказан.

Сужение типов — главная повседневная работа

Широкий тип (string | number, unknown, User | null) нужно довести до конкретного. Компилятор умеет читать обычные проверки JavaScript:

function f(x: string | number) {
  if (typeof x === "number") return x.toFixed(2);   // здесь x — number
  return x.trim();                                  // а здесь уже string
}

if (user === null) return;        // дальше user точно не null
if ("email" in contact) …         // сужение по наличию поля
if (Array.isArray(v)) …           // сужение массива
if (e instanceof Error) …         // работает: класс существует в рантайме

Дискриминированные объединения

Самый полезный приём для состояний. У всех вариантов есть общее поле-метка с литеральным типом, и проверка этого поля сужает весь объект целиком:

type State =
  | { status: "loading" }
  | { status: "error"; error: string }
  | { status: "ready"; data: User[] };

function render(s: State) {
  switch (s.status) {
    case "loading": return spinner();
    case "error":   return s.error;      // поле доступно только здесь
    case "ready":   return list(s.data);
  }
}

Такой тип запрещает невозможные состояния: не бывает «загрузка и данные одновременно», а поле error нельзя случайно прочитать в успешной ветке. Это лучше, чем три независимых булевых флага.

Исчерпывающая проверка через never

default: {
  const _exhaustive: never = s;      // добавили новый вариант — здесь ошибка компиляции
  throw new Error("неизвестный статус");
}

never — тип, у которого нет ни одного значения. Если все варианты разобраны, до default доходит именно он, и присваивание проходит. Стоит добавить в объединение четвёртый статус — компилятор покажет все места, где его забыли обработать.

Дженерики: связь между входом и выходом

Дженерик нужен не для «универсальности», а чтобы сохранить связь типов аргумента и результата:

function first(arr: unknown[]): unknown { … }   // тип потерян
function first<T>(arr: T[]): T | undefined { … } // тип сохранён

first([1, 2, 3]);        // number | undefined
first(["a", "b"]);       // string | undefined

Ограничение extends задаёт, что от типа требуется:

function byId<T extends { id: number }>(items: T[], id: number) {
  return items.find((i) => i.id === id);   // вернётся именно T, а не «что-то с id»
}

Признак лишнего дженерика. Если параметр типа встречается в сигнатуре ровно один раз, он ничего не связывает — его можно заменить обычным типом. <T>(x: T) => void — это просто (x: unknown) => void.

Мелочи, которые решают споры

  • interface или type: для формы объекта они почти взаимозаменяемы. type умеет объединения и пересечения, interface — слияние объявлений. Практический совет: выбрать один стиль в проекте и не спорить.
  • strict — главный флаг. Без strictNullChecks null входит в любой тип, и весь смысл проверок теряется.
  • Не аннотировать очевидное: вывод типов работает хорошо. Аннотации нужны на границах — параметры функций, публичные возвращаемые значения, форма состояния.
  • Выводить типы из данных, а не дублировать их: typeof config, keyof User, User["id"], Pick, Omit, Partial, Record.
  • satisfies проверяет, что значение подходит под тип, но не расширяет его до этого типа: конкретика литералов сохраняется.
Что уносим с собой. Типы стираются при сборке, поэтому as — обещание, а не проверка, и данные с границы разбирают как unknown. Совместимость структурная: важна форма, а не имя. any выключает проверку и заражает код, unknown заставляет сузить. Сужение делается обычными проверками JS, состояния описываются дискриминированным объединением, полнота разбора страхуется через never. Дженерик оправдан, только если связывает вход с выходом.
