Refs, формы и StrictMode

Три вопроса теста ты угадала: во что компилируется JSX (#34), как надёжно увеличить счётчик при группировке обновлений (#38) и зачем нужен useRef (#45). Все три — про одно: React работает не с экраном, а со своим описанием экрана. Понятно, где эта граница, — понятно и когда нужен ref, и почему счётчик отстаёт, и что делает StrictMode.

JSX — это вызовы функций

JSX не попадает в браузер. Сборщик превращает его в обычный JavaScript:

<button className="ok" onClick={f}>Да</button>

    ↓ компиляция

React.createElement("button", { className: "ok", onClick: f }, "Да")

Результат такого вызова — не DOM-узел, а простой объект: тип, пропсы, дети. Компонент, возвращая JSX, возвращает описание того, что должно быть на экране. Сопоставлением описания с реальным DOM занимается React отдельно.

Отсюда следуют мелочи, которые иначе выглядят произволом. class пишется как className, потому что это ключ объекта, а class — зарезервированное слово. Компонент обязан начинаться с большой буквы: со строчной буквы имя попадёт в createElement строкой и будет понято как HTML-тег. Возвращать нужно одно значение — поэтому и появился фрагмент <>…</>.

Состояние — это снимок, а не переменная

Внутри одного рендера значение состояния зафиксировано. Обработчик, созданный в этом рендере, видит именно то значение, которое было при его создании, — даже если вызвать его позже.

const [n, setN] = useState(0);

function onClick() {
  setN(n + 1);   // n здесь = 0
  setN(n + 1);   // n здесь ВСЁ ЕЩЁ 0
  setN(n + 1);   // и здесь тоже
}                // итог: 1, а не 3

React группирует обновления (batching): за один обработчик он не перерисовывает три раза, а собирает изменения и делает один рендер. Все три вызова записали «поставь 1».

Надёжный способ — функциональная форма: она получает не снимок, а актуальное значение из очереди.

setN(prev => prev + 1);
setN(prev => prev + 1);
setN(prev => prev + 1);   // итог: 3

Правило простое: если новое значение зависит от предыдущего — функциональная форма, всегда. Особенно в таймерах, подписках и асинхронном коде, где между созданием обработчика и его вызовом проходит время и снимок успевает устареть.

useRef: коробка, переживающая рендеры

useRef возвращает объект { current }, который не меняется между рендерами. Записать в .current можно что угодно, и React на это никак не реагирует.

useStateuseRef
Изменение вызывает рендерданет
Значение переживает рендердада
Можно менять во время рендеранетнет (только в эффектах и обработчиках)
Для чеговсё, что видно на экраневсё, что на экран не влияет

Два законных применения:

  1. Ссылка на DOM-узел. Атрибут ref на теге — и React после монтирования положит в .current настоящий элемент: inputRef.current.focus().
  2. Хранение служебного значения. Id таймера, предыдущее значение пропса, флаг «первый рендер», счётчик, который не показывают. Обычная переменная внутри компонента для этого не годится — она пересоздаётся на каждом рендере.
Чего ref не делает. Он не заменяет состояние: запись в .current не перерисовывает компонент, и на экране ничего не изменится. Если значение видно пользователю — это состояние. Обратное тоже верно: класть в состояние то, что на экран не влияет, — лишние рендеры.

Читать ref.current во время рендера нельзя: на первом рендере DOM-узла ещё нет (там null), а React не гарантирует согласованности. Место для работы с ref — эффекты и обработчики событий.

Управляемые и неуправляемые поля

У поля ввода есть собственное внутреннее состояние — то, что в нём набрано. Вопрос в том, кто им владеет.

Управляемое (controlled)Неуправляемое (uncontrolled)
Источник истинысостояние Reactсам DOM-узел
Как пишетсяvalue={v} + onChangedefaultValue + ref
Значение читаетсяиз состояния в любой моментиз ref.current.value, обычно при отправке
Валидация на лету, маски, зависимые поляестественнонеудобно
Рендер на каждое нажатиеданет

Практика: сложная форма с проверками по ходу ввода — управляемая; простая форма «набрал и отправил», особенно большая, — неуправляемая, она дешевле.

Частая ошибка. value={v} без onChange даёт поле, в котором невозможно печатать: React возвращает значение из состояния после каждого нажатия. Второй вариант той же ошибки — начать с value={undefined}, а потом подставить строку: поле переключится из неуправляемого в управляемое, и React напишет об этом предупреждение. Для «только чтение» есть readOnly.

key: чем список отличается от массива

Сопоставляя старое описание с новым, React должен понять, какой элемент списка какому соответствует. Для этого и нужен key — устойчивое имя строки.

Индекс массива в качестве key — источник ошибок, которые выглядят мистикой. Удалили первый элемент — у всех остальных сместились индексы, и React решает, что содержимое строк изменилось, а не что строка исчезла. Состояние внутри строк (набранный текст, раскрытость, фокус) остаётся на прежних позициях и уезжает не к тем данным.

Индекс допустим только там, где список неизменен: не переупорядочивается, не фильтруется, ничего не добавляется и не удаляется. В остальных случаях — идентификатор самой сущности.

Полезное следствие: смена key у компонента — законный способ сбросить его состояние. <Form key={userId} /> при смене пользователя размонтирует старую форму и смонтирует новую, чистую.

StrictMode: почему всё случается дважды

<StrictMode> — обёртка для разработки, в продакшн-сборке не делающая ничего. В режиме разработки она намеренно:

  • вызывает функции компонентов, редьюсеры и инициализаторы состояния дважды;
  • монтирует компонент, сразу размонтирует и монтирует снова — то есть прогоняет эффект → очистку → эффект;
  • предупреждает об устаревших приёмах.

Это не баг и не то, что нужно «выключить, чтобы не мешало». Двойной вызов ловит компоненты с побочными эффектами в теле рендера: если функция чистая, второй вызов не даёт никакой разницы. Двойной монтаж ловит эффекты без очистки: подписка, таймер или запрос, который не отменяется, при повторном монтаже удвоится — и это станет видно сразу, а не в проде.

useEffect(() => {
  const id = setInterval(tick, 1000);
  return () => clearInterval(id);   // без этой строки в StrictMode пойдут два таймера
}, []);

Как читать симптомы. «Запрос уходит дважды» — эффект не отменяет запрос (нужен AbortController). «Счётчик прыгает через один» — состояние меняется прямо в теле компонента. «Подписок становится две» — нет функции очистки. Во всех трёх случаях StrictMode не создал проблему, а показал её.
