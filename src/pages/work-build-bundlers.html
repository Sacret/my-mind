Сборка: бандлеры, tree shaking, code splitting

Вопрос #49 — «что такое tree shaking» — единственный в тесте про сборку, и он не сошёлся. Сборка выглядит как чужая территория: конфиг написан один раз, дальше «просто работает». Но именно она решает, сколько килобайт получит пользователь, и именно из-за неё библиотека на 300 килобайт иногда занимает в бандле три.

Зачем вообще сборщик

Браузер умеет загружать модули сам — <script type="module"> работает без всякой сборки. Но сотни отдельных файлов означают сотни запросов, а node_modules с его import "lodash" браузеру вообще непонятен: голых имён пакетов он не разрешает.

Сборщик решает четыре задачи:

  1. Разрешение модулей — превращает import "lodash" в путь к настоящему файлу.
  2. Склейка — собирает граф зависимостей в несколько файлов вместо тысячи.
  3. Трансформация — TypeScript, JSX, современный синтаксис под нужные браузеры, CSS, картинки.
  4. Оптимизация — минификация, tree shaking, разбиение на части, хэши в именах.

Работает он с графа зависимостей: от точки входа обходит все import, строит граф модулей и по нему решает, что попадёт в выдачу.

Tree shaking: выбрасывание неиспользуемого

Tree shaking — это удаление из бандла кода, который ниоткуда не импортируется. Название буквальное: дерево зависимостей трясут, и мёртвые ветки осыпаются.

// utils.js
export function used()   { … }
export function unused() { … }   ← в бандл не попадёт

// main.js
import { used } from "./utils";

Ключевое условие: это работает только с ES-модулями (import/export). Причина в том, что они статические: список импортов известен до запуска кода, его видно простым разбором файла. У CommonJS такого нет:

const name = условие ? "used" : "unused";
const fn = require("./utils")[name];   // что именно нужно — известно только в рантайме

Раз состав импорта вычисляется во время работы, сборщик обязан оставить модуль целиком. Отсюда практический совет: у библиотеки в package.json должно быть поле module или условный экспорт с ESM-сборкой — иначе тряска её не берёт.

Побочные эффекты рушат tree shaking. Если модуль при импорте что-то делает — правит прототип, регистрирует плагин, пишет в глобальный объект, — выбросить его нельзя: неизвестно, на что это повлияет. Сборщик перестраховывается и оставляет всё. Помечается это полем "sideEffects": false в package.json (или списком файлов-исключений, обычно CSS): им библиотека обещает, что её модули чисты.

Соседнее понятие — dead code elimination: выбрасывание кода, до которого не дойдёт исполнение (if (false), ветка после return). Именно так исчезает отладочный код при подстановке process.env.NODE_ENV === "production". Tree shaking работает на уровне графа модулей, DCE — внутри одного файла.

Code splitting: не отдавать всё сразу

Один большой бандл означает, что пользователь скачивает и разбирает весь код приложения ради первой страницы. Разбиение кода режет бандл на части, которые грузятся по мере надобности.

Главный инструмент — динамический импорт. Он возвращает промис и служит сборщику указанием: с этого места начинается отдельный кусок.

// вместо статического импорта на верхнем уровне
const { Chart } = await import("./Chart.js");

// в React — то же самое, обёрнутое в компонент
const Chart = lazy(() => import("./Chart"));
<Suspense fallback={<Spinner />}><Chart /></Suspense>

Что резать в первую очередь: маршруты (страница профиля не нужна на странице входа), тяжёлые редкие виджеты (редактор, графики, карты), модальные окна, админскую часть, локали.

Второй приём — выделение общих зависимостей. Библиотеки меняются реже своего кода, поэтому их выносят в отдельный чанк. Тогда при выкладке новой версии пользователь докачивает только изменившийся кусок, а react с прочим берёт из кэша.

Кэш и хэши в именах

Файл main.a3f9c1.js называется так не для красоты: хэш в имени — это отпечаток содержимого. Изменилось содержимое — изменилось имя, и браузер обязан скачать новый файл. Не изменилось — имя прежнее, файл берётся из кэша.

Отсюда стандартная схема: HTML отдаётся без кэша (он маленький и содержит ссылки на актуальные имена), а всё с хэшем в имени — с кэшем на год. И отсюда же требование к разбиению: неудачное разбиение, при котором любая правка меняет хэш общего чанка, обнуляет весь смысл кэширования.

Ключевая идея Vite. Старый сборщик, чтобы показать страницу в разработке, должен собрать проект целиком. Vite этого не делает: браузер сам запрашивает модули, а Vite на лету преобразует только те файлы, которые действительно понадобились. Отсюда и разница «тридцать секунд против трёхсот миллисекунд» на большом проекте.

Как читать вес бандла

Когда сборка вдруг растолстела, порядок действий один и тот же:

  1. Построить карту бандла (визуализатор есть у любого сборщика) и посмотреть, кто занимает место.
  2. Проверить, не втащена ли библиотека целиком там, где нужна одна функция — и есть ли у неё ESM-сборка.
  3. Проверить полифилы и локали: moment и подобные пакеты тянут все языки мира, если их не ограничить.
  4. Вынести в динамический импорт то, что не нужно на первом экране.
  5. Сравнивать размер после сжатия — пользователь получает gzip или brotli, и соотношение между библиотеками там другое.
