Производительность фронтенда: рендеринг и Core Web Vitals

«Тормозит» — это не одно свойство, а как минимум три разных: долго не появляется содержимое, страница прыгает под руками, интерфейс не отвечает на нажатие. Причины у них разные, и лечатся они разным. Урок о том, как браузер рисует страницу и где именно теряются миллисекунды.

Как браузер превращает файлы в картинку

  1. Парсинг HTML → дерево DOM. Встреченный <script> без атрибутов останавливает парсер: скрипт может дописать разметку.
  2. Парсинг CSS → CSSOM. CSS блокирует отрисовку: рисовать неоформленный текст браузер не станет.
  3. Layout — расчёт геометрии: что где лежит и какого размера.
  4. Paint — заливка пикселей: цвета, тени, текст.
  5. Composite — сборка готовых слоёв в кадр, в том числе на видеокарте.

Ключ ко всей оптимизации анимаций. Изменение width, top, margin запускает цепочку с самого начала — layout, paint, composite. Изменение transform и opacity обрабатывается на последнем шаге: геометрия не пересчитывается. Поэтому сдвиг делают через transform: translateX(), а не через left.

Скрипты и порядок загрузки

ФормаЧто делает

INP (Interaction to Next Paint) в 2024 году заменил прежнюю метрику FID. Разница принципиальная: FID мерил только задержку до начала обработки первого клика, INP — полное время от действия до перерисованного кадра, по всем взаимодействиям. Обмануть его «быстрым началом обработки» уже нельзя.

Главный поток и длинные задачи

JavaScript, layout, paint и обработка ввода живут в одном потоке. Пока выполняется функция, браузер не может ни отреагировать на клик, ни отрисовать кадр. Задача длиннее 50 мс считается длинной, а на кадр при 60 к/с есть всего 16 мс.

Что с этим делают:

  • Дробят работу. Обработку большого списка режут на куски и отдают управление браузеру между ними.
  • Выносят в Web Worker тяжёлые вычисления — разбор больших JSON, расчёты, обработку изображений.
  • Ограничивают частоту обработчиков ввода и прокрутки через debounce и throttle.
  • Сокращают работу на рендер: мемоизация, виртуализация длинных списков, пагинация вместо «показать все 5000 строк».

Layout thrashing

// плохо: чтение размера после каждой записи заставляет пересчитывать layout синхронно
for (const el of items) {
  el.style.height = el.offsetHeight + 10 + "px";
}

// хорошо: сначала все чтения, потом все записи
const heights = items.map((el) => el.offsetHeight);
items.forEach((el, i) => { el.style.height = heights[i] + 10 + "px"; });

Браузер копит изменения стилей и применяет их пачкой. Но запрос offsetHeight, getBoundingClientRect или scrollTop требует актуальной геометрии — и вынуждает пересчитать layout немедленно. Чередование чтения и записи в цикле превращает один пересчёт в сотню.

Что обычно весит больше всего

  • Картинки. Современный формат вместо PNG, srcset и sizes под ширину экрана, loading="lazy" для всего ниже первого экрана — но не для LCP-картинки, ей наоборот ставят fetchpriority="high". Обязательно width и height в разметке: место резервируется заранее и CLS не растёт.
  • Сторонние скрипты. Аналитика, чаты, виджеты, реклама — частая причина длинных задач, при этом не приносят пользователю ничего. Грузить отложенно и пересматривать список.
  • Шрифты. До загрузки текст либо невидим, либо показан запасным шрифтом. font-display: swap плюс preload нужного начертания; чем ближе метрики запасного шрифта, тем меньше прыжок при подмене.
  • Собственный JavaScript. Разбиение по маршрутам и отложенная загрузка тяжёлых частей — про это отдельный урок про сборку.

Сеть тоже настраивается: сжатие ответов, кэширующие заголовки с хэшем в имени файла, HTTP/2 и HTTP/3, раздача статики через CDN.

Измерять, а не угадывать

ИнструментЧто показывает
Lighthouse и панель Performanceлабораторные данные: один прогон в контролируемых условиях, удобно сравнивать «до и после»
Полевые данные (RUM)что происходит у настоящих пользователей — с их устройствами и сетью; Core Web Vitals оценивают именно по ним
Профайлер, вкладка Performanceкто именно занимал главный поток и где были длинные задачи

Обязательный приём. Замедлить процессор в четыре-шесть раз и сеть до мобильной прямо в devtools. На рабочем ноутбуке с быстрым интернетом почти всё выглядит мгновенным, а половина аудитории сидит на среднем телефоне.

Порядок работы всегда один: измерить → найти узкое место → починить именно его → измерить снова. Оптимизация без замера обычно улучшает то, что и так не мешало.

Что уносим с собой. Путь кадра: DOM и CSSOM → layout → paint → composite; transform и opacity не трогают геометрию, top и width трогают. Скрипты подключают с defer. Core Web Vitals: LCP до 2,5 с, INP до 200 мс, CLS до 0,1; INP заменил FID и меряет весь путь от нажатия до кадра. Главный поток один: задачи длиннее 50 мс убивают отклик, чтение геометрии вперемешку с записью даёт layout thrashing. Размеры у картинок спасают от прыжков, LCP-картинку не делают ленивой. Профилировать при замедленном процессоре и по полевым данным.
