Git: merge против rebase, конфликты, история

Новая область. Git обычно используют десятком заученных команд, и любое отклонение от сценария превращается в панику. Между тем модель у него крошечная: коммит — это снимок дерева со ссылкой на родителя, ветка — подвижный указатель на коммит. Почти всё поведение выводится из этих двух фраз.

Модель

  • Коммит — снимок всего дерева файлов плюс ссылка на родителя (или на двух родителей у слияния) плюс метаданные. Идентификатор — хеш содержимого, поэтому изменить коммит нельзя: можно только создать новый.
  • Ветка — файл с одним хешем внутри. Создание ветки не копирует ничего и стоит ноль.
  • HEAD — указатель на текущую ветку.
  • Тег — тот же указатель, только неподвижный.

Из «коммит неизменяем» следует главное правило безопасности: всё, что «переписывает» историю, на самом деле создаёт новые коммиты, а старые остаются, пока их не соберёт сборщик мусора. Поэтому почти любую катастрофу можно откатить.

Три области

рабочий каталог  →  индекс (stage)  →  репозиторий
      git add            git commit

git diff              рабочий каталог против индекса
git diff --staged     индекс против последнего коммита
git restore файл      вернуть файл из индекса (отменить правку)
git restore --staged  убрать из индекса, правки сохранить

Понимание, что индекс — отдельная область, а не «список файлов на коммит», объясняет, почему git diff иногда «ничего не показывает» после git add.

merge против rebase

Обе команды решают одну задачу — перенести работу ветки в основную линию, — но делают это противоположным образом.

mergerebase
Что делаетсоздаёт коммит слияния с двумя родителямипереносит коммиты поверх новой базы, создавая их копии
Историясохраняется как было, с ветвлениемстановится линейной
Хеши коммитовне меняютсяменяются — это новые коммиты
Конфликтыразбираются один размогут возникать на каждом переносимом коммите
git merge main      # влить main в текущую ветку
git rebase main     # переложить свои коммиты поверх main
Золотое правило rebase. Не переписывать историю, которую уже кто-то скачал. Rebase меняет хеши, и у коллег остаются старые коммиты — при следующем pull ветка задваивается. Rebase — для своей ветки до публикации; для общих веток merge.

Отдельно: git pull по умолчанию делает merge и засоряет историю коммитами «Merge branch 'main'». Обычно настраивают git config --global pull.rebase true.

Fast-forward — частный случай: если в основной ветке ничего нового, указатель просто передвигается вперёд, и коммита слияния не возникает. --no-ff заставляет создать его принудительно, чтобы в истории было видно факт ветвления.

Конфликты

Конфликт возникает, когда две стороны изменили одни и те же строки. Git размечает файл:

<<<<<<< HEAD
то, что в текущей ветке
=======
то, что во входящей
>>>>>>> feature

Порядок разбора: отредактировать файл, оставив нужное и удалив маркеры → git add → git commit при merge или git rebase --continue при rebase. Выход из положения, если стало страшно: git merge --abort или git rebase --abort возвращают всё в исходное состояние.

Кто есть кто в маркерах. При merge «HEAD» — ваша ветка. При rebase они меняются местами: «HEAD» — это ветка, на которую вы переносите, а «входящее» — ваш собственный коммит. Это самая частая причина выбрать не ту сторону.

Как отменять

КомандаЧто делаетКогда
git revert <hash>новый коммит, отменяющий указанныйистория опубликована — единственный безопасный вариант
git reset --soft HEAD~1убирает коммит, правки остаются в индексепеределать сообщение или состав коммита
git reset --mixed HEAD~1убирает коммит и индекс, файлы целыпересобрать коммит заново
git reset --hard HEAD~1убирает всё, включая правки в файлахосторожно: несохранённое пропадёт
git commit --amendзаменяет последний коммит новымтолько до публикации

Спасательный круг — git reflog. Он хранит, где HEAD побывал за последние недели, включая коммиты, потерянные после reset и неудачного rebase. Восстановление — git reset --hard <hash из reflog>. Практически единственный способ по-настоящему потерять работу — это потерять несохранённые изменения в рабочем каталоге: то, что попало хотя бы в один коммит, находится почти всегда.

Полезное на каждый день

git switch -c feature        создать ветку и перейти (раньше checkout -b)
git stash / git stash pop    отложить незакоммиченное и вернуть
git log --oneline --graph    история с ветвлениями
git log -p файл              как менялся конкретный файл
git blame файл               кто и когда написал каждую строку
git bisect start             бинарный поиск коммита, сломавшего поведение
git cherry-pick <hash>       взять один коммит из другой ветки

git bisect заслуживает отдельного упоминания: это тот же бинарный поиск из урока про O-нотацию. Среди тысячи коммитов виновный находится за десять проверок вместо тысячи.

О содержании коммитов

  • Один коммит — одно изменение. Это не эстетика: только так работают revert, cherry-pick и bisect. Коммит на пятьсот файлов невозможно ни откатить, ни разобрать.
  • Сообщение объясняет «почему», а не «что». Что изменилось, видно из диффа; зачем — нигде.
  • Не коммитить секреты. Удаление ключа следующим коммитом ничего не даёт: он остаётся в истории и подлежит отзыву, а не удалению.
  • git add -p позволяет собрать коммит по кускам, когда в файле смешались два разных изменения.
Что уносим с собой. Коммит — неизменяемый снимок со ссылкой на родителя, ветка — подвижный указатель. Merge сохраняет ветвление, rebase делает историю линейной, но меняет хеши — и потому не применяется к опубликованным веткам. Конфликт разбирается вручную, abort всегда доступен, при rebase стороны в маркерах меняются местами. revert безопасен для общей истории, reset — для локальной, reflog возвращает потерянное.
