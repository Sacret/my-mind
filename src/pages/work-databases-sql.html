SQL: join, индексы, нормализация

Новая область, но опирается на пройденное: индекс — это структура данных из второго урока основ, а его выигрыш — та самая разница между O(n) и O(log n). Здесь разберём, как база хранит данные, почему запрос иногда работает секунду вместо миллисекунды и что означает «нормализовать таблицу».

Декларативность: чем SQL отличается от кода

В SQL описывается какой результат нужен, а не как его получить. План выполнения выбирает планировщик, опираясь на статистику по данным. Отсюда два следствия, определяющие всю практику:

  • Один и тот же запрос на разных объёмах данных выполняется принципиально по-разному — база может пойти по индексу или прочитать таблицу целиком.
  • Оптимизация — это не переписывание запроса «покрасивее», а чтение плана через EXPLAIN и устранение того, что в нём видно.

Порядок, в котором на самом деле выполняется запрос

Написан запрос в одном порядке, выполняется в другом — и это объясняет большинство ошибок новичка:

пишем:     SELECT … FROM … JOIN … WHERE … GROUP BY … HAVING … ORDER BY … LIMIT
выполняется: FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT

Отсюда:

  • WHERE фильтрует строки до группировки, HAVING — группы после. Условие на COUNT(*) может стоять только в HAVING.
  • Псевдоним из SELECT нельзя использовать в WHERE — на тот момент его ещё не существует. В ORDER BY можно: он выполняется позже.

JOIN

Соединение сопоставляет строки двух таблиц по условию. Различаются они тем, что делать со строками без пары.

ТипЧто возвращает
INNER JOINтолько строки, где пара нашлась в обеих таблицах
LEFT JOINвсе строки левой; для непарных — NULL в полях правой
RIGHT JOINзеркально; на практике почти не используется
FULL JOINвсе строки обеих таблиц
CROSS JOINвсе пары со всеми — декартово произведение
-- пользователи и их заказы, включая тех, у кого заказов нет
SELECT u.name, COUNT(o.id) AS orders
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id, u.name;
Ловушка, съедающая LEFT JOIN. Условие на правую таблицу, вынесенное в WHERE, превращает LEFT JOIN в INNER: строки с NULL отсеиваются проверкой. Условие должно стоять в ON: 
LEFT JOIN orders o ON o.user_id = u.id AND o.status = 'paid'   -- верно
LEFT JOIN orders o ON o.user_id = u.id WHERE o.status = 'paid' -- LEFT сломан

Вторая частая неожиданность — размножение строк. Если у пользователя три заказа, после JOIN он встретится трижды, и SUM по его полям утроится. Поэтому агрегировать обычно нужно до соединения или использовать COUNT(DISTINCT …).

Индексы

Без индекса база читает всю таблицу — O(n). Индекс обычно B-дерево: отсортированная структура, дающая поиск за O(log n). Это тот же выигрыш, что бинарный поиск против перебора.

Что нужно знать на практике

  • Индекс ускоряет чтение и замедляет запись. Каждый INSERT и UPDATE обновляет все индексы таблицы. Пять индексов «на всякий случай» — заметный налог на запись.
  • Составной индекс работает слева направо. Индекс (city, age) помогает запросу по city и по city + age, но не по одному age.
  • Функция над колонкой отключает индекс. WHERE LOWER(email) = … не воспользуется индексом по email: нужен индекс по выражению или сравнение без функции. То же с WHERE date(created_at) = … — заменяется диапазоном.
  • LIKE '%text' не индексируется — префикс неизвестен. LIKE 'text%' индексируется.
  • Покрывающий индекс содержит все нужные запросу колонки, и база не обращается к самой таблице.
  • На маленькой таблице индекс не нужен — прочитать сотню строк дешевле, чем идти через дерево. Планировщик это учитывает и может проигнорировать индекс.
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 42;

Seq Scan   ← читается вся таблица: индекса нет или он не подошёл
Index Scan ← используется индекс

Нормализация

Смысл один: каждый факт хранится в одном месте. Иначе при изменении его придётся править в нескольких строках, и рано или поздно они разойдутся.

Три первые формы на практике покрывают почти всё:

  1. 1НФ — в ячейке одно значение, а не список. Вместо колонки tags = "a,b,c" — отдельная таблица.
  2. 2НФ — неключевые поля зависят от всего ключа, а не от его части.
  3. 3НФ — неключевые поля не зависят друг от друга. Если в таблице заказов лежит city и country, а страна определяется городом, страну надо вынести.

Обратный приём — денормализация: сознательное дублирование ради скорости чтения. Хранить в таблице постов счётчик комментариев вместо COUNT при каждом запросе — нормальное решение, но оно создаёт второй источник правды, который нужно поддерживать в согласии.

Историческое исключение. Цена товара в заказе копируется в строку заказа намеренно: это не дублирование, а фиксация факта на момент покупки. Ссылка на текущую цену исказила бы прошлые заказы при её изменении.

NULL

NULL — не значение, а его отсутствие, и сравнения с ним дают не true и не false, а «неизвестно»:

NULL = NULL        → NULL, а не true
x <> 'a'           → не вернёт строки, где x = NULL
IS NULL / IS NOT NULL   ← единственный корректный способ проверки

COUNT(*)           считает все строки
COUNT(column)      пропускает NULL — типичное расхождение в отчётах

Транзакции

Транзакция — группа операций, применяемая целиком или не применяемая вовсе. Свойства принято обозначать как ACID: атомарность, согласованность, изолированность, долговечность.

Практически важна изолированность: одновременные транзакции могут видеть промежуточные состояния друг друга. Классический дефект — «прочитал, посчитал, записал»: два процесса читают остаток 10, оба вычитают 3, оба пишут 7 вместо 4. Лечится атомарным UPDATE … SET balance = balance - 3, блокировкой SELECT … FOR UPDATE или более строгим уровнем изоляции.

Отдельно про инъекции

// нельзя: строка пользователя становится частью запроса
db.query("SELECT * FROM users WHERE email = '" + email + "'");

// нужно: параметр передаётся отдельно от текста запроса
db.query("SELECT * FROM users WHERE email = $1", [email]);

Экранирование вручную — не решение: параметризованный запрос отделяет код от данных на уровне протокола, и это единственная надёжная защита.

Что уносим с собой. SQL декларативен, оптимизация начинается с EXPLAIN. WHERE до группировки, HAVING после. Условие на правую таблицу LEFT JOIN должно быть в ON, иначе соединение станет внутренним. Индекс даёт O(log n), но замедляет запись; функция над колонкой и LIKE '%…' его отключают. Нормализация — один факт в одном месте, денормализация — осознанный обмен на скорость. NULL сравнивается только через IS NULL. Параметризованный запрос вместо конкатенации.
