Мутации, ссылки и иммутабельность

В тесте две ошибки оказались на самом деле одной: про map ты ответила «изменяет исходный массив», а причину, почему нельзя писать state.push(x), назвала «массивы в JS иммутабельны». Это одна тема, и она напрямую объясняет добрую половину багов в React.

Переменная хранит ссылку, а не объект

Начнём с фундамента, иначе всё остальное держаться не будет.

Примитивы (число, строка, булево, null, undefined) копируются по значению. Объекты и массивы — по ссылке: переменная хранит не сам объект, а адрес места, где он лежит.

const a = { n: 1 };
const b = a;      // скопировали ссылку, не объект
b.n = 2;
console.log(a.n); // 2 — это один и тот же объект

Отсюда и сравнение: два объекта равны, только если это буквально один объект.

{ n: 1 } === { n: 1 }   // false — разные адреса
[] === []               // false

Про const. Он запрещает переприсваивать ссылку, но не трогает содержимое. Поэтому const arr = [1,2,3]; arr.push(4) совершенно легально: ссылка та же, изменилось наполнение. А вот arr = [] уже упадёт с ошибкой. Массивы в JS не иммутабельны — иммутабельность это дисциплина, которую соблюдает программист.

Два вида методов массива

Главное, что стоит выучить наизусть: одни методы меняют исходный массив и возвращают что-то другое, вторые не трогают исходный и возвращают новый.

Мутируют исходныйВозвращают новый
push, pop, shift, unshift, splice, sort, reverse, fill map, filter, slice, concat, flat, toSorted, toReversed, with

map — из правой колонки: он создаёт новый массив той же длины, применив функцию к каждому элементу. Исходный остаётся нетронутым.

const nums = [1, 2, 3];
const doubled = nums.map(n => n * 2);
console.log(nums);    // [1, 2, 3] — не изменился
console.log(doubled); // [2, 4, 6]

Мнемоника по именам: splice режет живой массив, slice отрезает копию. Похожие названия, противоположное поведение.

Особая ловушка: sort и reverse

Их легко принять за «возвращающие», потому что они действительно что-то возвращают — но возвращают тот же самый массив, уже перевёрнутым:

const sorted = props.items.sort();  // упс: мы только что
                                    // отсортировали чужой массив из пропсов

Правильно — сначала копия, либо новые методы:

const sorted = [...props.items].sort();   // работает везде
const sorted = props.items.toSorted();    // ES2023, короче и честнее

Ещё одна деталь про sort: без функции сравнения он сортирует как строки. [10, 9, 100].sort() даст [10, 100, 9]. Для чисел нужен компаратор: sort((a, b) => a - b).

Копирование поверхностное, и это важно

Spread и Object.assign копируют только верхний уровень. Вложенные объекты остаются общими:

const user = { name: 'Аня', address: { city: 'Москва' } };
const copy = { ...user };
copy.address.city = 'Казань';
console.log(user.address.city);  // 'Казань' — исходный тоже изменился!

Чтобы обновить вложенное поле по-настоящему, копию делают на каждом уровне пути:

const copy = { ...user, address: { ...user.address, city: 'Казань' } };

Для глубокого копирования целиком есть встроенный structuredClone(obj). Он честно клонирует вложенность, но не умеет копировать функции и не всегда нужен: обычно достаточно скопировать только тот путь, который меняется.

Зачем всё это React

Теперь главное. React решает, нужно ли перерисовывать компонент, сравнивая старое и новое состояние по ссылке (через Object.is). Он не обходит массив поэлементно — это было бы слишком дорого.

// не сработает
const [items, setItems] = useState([]);
items.push(newItem);      // мутация: ссылка не изменилась
setItems(items);          // React сравнивает: та же ссылка → рендера нет
// сработает
setItems([...items, newItem]);       // новый массив → новая ссылка → рендер

Уточнение к твоему ответу в тесте. Причина не в том, что «массивы иммутабельны» — они как раз нет. Причина в том, что React сравнивает ссылки и не замечает изменений внутри того же объекта. Мутация тихо меняет данные, а интерфейс остаётся старым — баг без ошибки в консоли, самый неприятный вид.

Шпаргалка обновлений состояния

// добавить
setItems([...items, item]);

// удалить по id
setItems(items.filter(i => i.id !== id));

// изменить один элемент
setItems(items.map(i => i.id === id ? { ...i, done: true } : i));

// отсортировать
setItems([...items].sort((a, b) => a.order - b.order));

// вложенное поле объекта
setUser({ ...user, address: { ...user.address, city } });

Заметь, что весь список собран из методов правой колонки таблицы: map, filter, spread. Это не совпадение — иммутабельный стиль и есть работа только «возвращающими» методами.

Побочный эффект: memo начинает работать

У этой дисциплины есть бонус. Раз новые данные — это всегда новая ссылка, дешёвая проверка prev !== next становится надёжным признаком изменения. На этом стоят React.memo, useMemo и массивы зависимостей у хуков.

Обратная сторона: если каждый рендер создавать новый объект там, где данные не менялись, все эти оптимизации сломаются — memo будет видеть «новую» ссылку каждый раз. Отсюда правило: новая ссылка ровно тогда, когда изменились данные. Ни чаще, ни реже.

Что уносим с собой. Объекты живут по ссылке, const защищает ссылку, а не содержимое. map, filter, slice возвращают новое; push, splice, sort, reverse мутируют. Spread копирует один уровень. React сравнивает ссылки — мутация состояния не вызывает рендер.
